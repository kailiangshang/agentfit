本文记录 AgentFit 在正式实现前已经讨论的内容、已经确认的决定、仍属于建议的方向、尚未决定的问题，以及这些设计如何对应 GOAI Agent Infra 赛道要求。

本文使用以下标记：

- **已确认**：讨论中已经明确认可，后续设计应以此为约束。
- **当前建议**：已有推荐方向，但仍可在后续设计中调整。
- **未决定**：尚未进入详细讨论，不能按既定需求实现。
- **不采用**：讨论过但当前明确不作为主路线。

## 1. 项目背景与方向变化

### 1.1 早期方向

早期讨论围绕算法团队的用户反馈排查、问题定位、周期性巡检以及飞书接入展开，并对 AgentTeams 的 Manager、Worker、Team、Human、Skill、文件同步、代码执行和定时任务进行了实际试用。

比赛目标明确后，原有垂直场景不再作为参赛主方向。原因不是它没有价值，而是常规客服、巡检、运维和反馈闭环已经有较多同类方案，不足以体现新的 Agent Infra 层价值。

### 1.2 选定的新方向

**已确认：** 参赛项目采用 Agent Team Preflight Lab 方向，并定名为 **AgentFit**。

AgentFit 不是又一个 Agent Builder，也不是通过聊天生成 Prompt 或 YAML 的咨询机器人。它解决的是 Agent 落地之前缺少决策和验证中间层的问题：

```text
业务材料与真实问题
→ 自动化边界分析
→ 最小候选方案
→ AgentTeams 真实部署
→ 统一任务试运行
→ 故障与异常验证
→ 证据比较
→ 可部署方案或否决结论
```

AgentFit 允许给出以下任一结论：

- 不应自动化；
- 使用确定性脚本；
- 使用单 Agent；
- 使用多 Agent；
- 当前证据不足，暂不实施。

这项“否定权”是 AgentFit 与 Agent 推销工具之间的重要区别。

## 2. 要解决的市场断层

**已确认：** 当前 Agent 市场存在两类典型方案及一个共同缺口。

1. 重型平台功能完整，但团队需要部署、学习和维护大量不需要的功能。
2. 轻型框架足够灵活，但要求使用者已经具备业务抽象、Agent 架构设计和工程开发能力。
3. 两类方案往往都假设使用者已经知道“应该构建什么”。

AgentFit 填补的中间层是：

> 从已有材料、流程和问题出发，识别适合自动化的部分，设计少量候选方案，在真实运行环境中进行可比较的试验，最终交付经过验证、可部署、可审计的最小方案。

### 2.1 竞品调研形成的创新边界

此前调研发现，“自然语言生成 Agent 工作流”已有直接近似项目或产品能力，例如：

- [BPAX](https://github.com/bpax-io/bpax)：业务流程中间表示及多框架配置生成；
- [Agentic Workflow Planner](https://github.com/imniteen/Agentic-Workflow-Planner)：通过对话生成 AutoGen YAML；
- [OpenAI Agent Workflow Wizard](https://github.com/jnyross/openai-agent-wizard)：使用多个设计和审查 Agent 生成架构规格；
- [Google Agent Simulation](https://docs.cloud.google.com/gemini-enterprise-agent-platform/optimize/evaluation/evaluate-simulated)：为既有 Agent 生成测试场景和模拟用户；
- [Agentic Workflow Compiler](https://github.com/jfriisj/agentic-workflow-generator)：将声明式规格编译为不同 Agent 配置。

因此，AgentFit 不能把“生成工作流”本身作为核心创新，也不能声称市场完全不存在同类项目。

当前差异化主张是：

```text
业务材料
→ 自动化边界
→ 多个最小候选团队
→ AgentTeams 真实部署
→ 相同任务集对照
→ 故障注入与人工介入
→ 真实证据评分
→ 可部署包与审计档案
```

上述竞品结论是此前调研快照，在最终提交前仍需重新核验其当前版本和能力。

## 3. 场景定义，而非用户限制

最初曾建议把目标用户限定为中小企业的技术负责人或 AI 落地负责人。该限制已被明确纠正。

**已确认：** AgentFit 不按职位、公司规模、行业或技术水平限制使用者，而是按场景定义。

适用场景是：

> 任何个人、团队或组织，只要拥有业务材料、现有流程或真实问题，希望判断其中哪些部分适合 Agent 化、应该采用什么 Agent 组合，并在正式投入前完成真实验证，都可以使用 AgentFit。

使用者可以是业务人员、技术人员、管理者、顾问、创业团队或研究团队。

为了描述完整业务流程，可以使用以下参与角色，但这些角色不是产品准入条件，也可以由同一个人兼任：

- 材料与问题提供者；
- 试运行审批者；
- 结果验收者；
- 部署执行者。

比赛 Demo 可以选择一个代表性场景，但不能把代表性操作者写成 AgentFit 的唯一目标用户。

## 4. 项目定位与两层架构

**已确认：** AgentFit 是一支运行在 AgentTeams 上的常驻元团队。

正式叙事为：

> AgentFit 是一支基于 AgentTeams 的虚拟 Agent 解决方案工程团队。

英文表达可使用：

> A Virtual Forward-Deployed Agent Engineering Team.

Preflight Lab 不是另一个独立产品，而是这支工程团队用于创建、试验和验证候选 Agent 团队的工程实验室。

### 4.1 两层结构

```text
AgentFit 常驻元团队
        ↓ 创建、试验和管理
临时候选 AgentTeams
        ↓ 真实运行并产生证据
选择、导出、归档或销毁
```

AgentFit 使用 AgentTeams 来设计、运行和验证新的 AgentTeams。

### 4.2 AgentTeams 与 AgentFit 的职责

| 层次 | 主要职责 |
| --- | --- |
| AgentTeams | Manager、Worker、Team、Human、Matrix 通信、共享文件、Skill/MCP、凭证、调度和生命周期 |
| AgentFit 元团队 | 材料理解、自动化边界、候选设计、试验组织、证据评估和工程交付 |
| 候选团队 | 接受统一任务、故障和验收标准的临时 AgentTeams |
| 可选交互层 | 材料提交、审批、进度和证据展示；尚未设计 |

**不采用：**

- 把 AgentFit 做成完全独立的外部 Web 平台，只把 AgentTeams 当容器后端；
- 把所有 AgentFit 产品能力直接修改进 AgentTeams Fork；
- 重新实现 AgentTeams 已经提供的通信、身份、文件、Skill 或 Worker 生命周期。

底层确有阻塞问题时，可以在独立的 AgentTeams Fork 中修复，但框架修改与 AgentFit 产品代码必须保持边界。

## 5. AgentFit 常驻元团队

讨论过 3、4、5 Agent 三种结构：

- 3 Agent 最轻，但 Manager 职责不清，试验执行与审计冲突明显；
- 4 Agent 可以分离交互，但试验执行者仍需要评价自己的结果；
- 5 Agent 能够形成事实、设计、执行和审计的职责分离。

**已确认：采用 5 Agent 常驻元团队。**

| Agent | 专业身份 | 核心职责 | 明确禁止 |
| --- | --- | --- | --- |
| `EngagementLead` | Agent 项目交付负责人 | 用户交互、项目状态、任务拆解、协调和审批 | 不直接设计候选方案，不修改评测结果 |
| `BusinessEngineer` | 业务发现工程师 | 阅读材料，提取事实、问题、约束、证据缺口和自动化边界 | 不决定最终 Agent 架构 |
| `AgentArchitect` | Agent 系统架构师 | 生成无 Agent、单 Agent、多 Agent 候选方案和试验规格 | 不部署候选团队，不评价自己的方案 |
| `ValidationEngineer` | 验证与可靠性工程师 | 创建临时团队、执行任务、注入故障并收集证据 | 试验开始后不能修改验收标准 |
| `GovernanceAuditor` | 治理与审计工程师 | 独立核验结果、安全边界和交付条件 | 只读访问证据，不能修改候选方案或运行记录 |

`EngagementLead` 最初被称为 `FitManager`，在专业工程团队叙事确定后更名。完整 Agent Identity 的字段和值尚未设计。

AgentTeams 中的具体资源拓扑、房间结构以及是否把 `EngagementLead` 直接映射为 Manager 资源仍属于 **未决定**；目前只确认逻辑职责关系。

## 6. 项目主流程

**已确认：** AgentFit 的项目主流程为：

```text
材料与问题
→ 业务理解
→ 自动化边界分析
→ 候选方案
→ 试验计划审批
→ AgentTeams 真实试运行
→ 证据比较
→ 方案导出或否决
→ 经验沉淀
```

对应的系统状态骨架为：

```text
Intake
→ Discover
→ Architect
→ Approve
→ Trial
→ Audit
→ Deliver
→ Learn
```

各阶段的核心含义：

1. 接收可能不完整的材料、问题、流程、约束和期望结果；
2. 形成带证据来源的统一项目档案；
3. 区分适合脚本、单 Agent、多 Agent、人工决策以及证据不足的环节；
4. 生成少量有意义的候选方案，不机械凑齐架构类型；
5. 使用统一任务、输入、验收标准和异常条件制定试验；
6. 经人工批准后，通过 AgentTeams 真实创建和运行候选团队；
7. 基于运行证据比较正确性、稳定性、人工介入、成本、复杂度和安全性；
8. 选择满足要求的最小方案，或者明确否决 Agent 化；
9. 将成功模式、失败原因和评测规则沉淀为可复用资产。

用户至少在以下两个阶段介入：

- 试运行前批准范围、权限和风险；
- 导出前确认最终方案及上线条件。

## 7. 协同模型

讨论过三种协同方式：

1. 纯 Workflow：可靠但难以适应未知问题；
2. 纯通信协同：灵活但状态不清、难审计；
3. 混合协同：确定性状态骨架、Agent 通信处理不确定问题、结构化状态保存正式结果。

**已确认：采用混合协同。**

### 7.1 各协同载体的职责

| 载体 | 职责 |
| --- | --- |
| Workflow/状态机 | 约束项目阶段、入口、完成条件和异常分支 |
| Matrix | 任务委派、讨论、质疑、通知和人工介入 |
| Project Dossier | 保存项目唯一可信状态、材料引用、决策和证据 |
| Task Envelope | 定义具体任务的输入、输出、验收标准、负责人和证据要求 |
| Trace | 记录状态变化、决策依据、工具调用、审批、创建和销毁操作 |

核心原则是：

> 聊天内容不是正式状态，只有结构化写入 Project Dossier 的结果才是正式状态。

Project Dossier、Task Envelope 和状态机的具体 Schema 尚未确定。

## 8. 受控自增长

**已确认：** AgentFit 应能够从项目中成长，但增长必须受控、可验证、可回滚。

不采用无限制地让 Agent 自行创建 Agent、修改自身身份或将未经验证的 Skill 直接投入使用。

### 8.1 项目内弹性成长

```text
发现能力缺口
→ 提交 Growth Proposal
→ AgentArchitect 设计临时专家或 Skill
→ 人工批准
→ AgentTeams 隔离创建临时 Worker
→ 执行专项任务
→ ValidationEngineer 测试
→ GovernanceAuditor 审核
→ 晋升、归档或销毁
```

新 Agent 默认具备以下约束：

- 只在隔离环境创建；
- 最小权限，优先只读访问；
- 受 Agent 数量、Token、时间和成本预算限制；
- 不能修改核心五 Agent 的身份和权限；
- 未经审计不能进入正式能力目录；
- 创建、变更、晋升和销毁必须保留 Trace；
- 审核失败必须可销毁并回滚到上一稳定状态。

### 8.2 跨项目累计成长

临时专家完成任务后，不是永久保留所有容器，而是把经过验证的部分沉淀为：

- Agent Identity 模板；
- 可复用 Skill；
- Team 组合模板；
- 测试与故障案例；
- 失败模式、适用条件和回滚经验。

后续项目检索和复用这些资产，但仍必须针对当前材料重新验证，不能因为模板曾经成功就直接跳过试验。

## 9. 项目交付与可复用资产

**已确认：每个项目产生项目专属交付和可复用资产两类成果。**

### 9.1 项目专属交付

- 当前业务的 AgentTeams 部署包；
- Agent、Skill 和工具配置；
- 测试结果与审计报告；
- 权限、审批、回滚和运行说明；
- 不适合自动化部分及否决原因。

### 9.2 可复用资产

- 业务发现和材料清单模板；
- 自动化边界判断规则；
- 无 Agent、单 Agent、多 Agent 方案模板；
- Agent Identity 模板；
- 可复用 Skill；
- MCP 或等价工具接口契约；
- Team 组合与协作模板；
- 测试任务、故障注入和评测模板；
- 交付报告、部署和回滚模板；
- 已知失败模式和适用条件。

项目方案不能直接复制进能力资产库。晋升流程为：

```text
项目验证
→ 审计通过
→ 去除项目敏感数据
→ 抽象可配置参数
→ 标注适用与不适用条件
→ 回归测试
→ 版本化发布
```

长期飞轮为：

```text
真实项目
→ 项目专属解决方案
→ 真实试运行和审计
→ 可复用部分抽象与晋升
→ 后续项目复用并重新验证
→ 证据和资产持续演进
```

## 10. GOAI Agent Infra 赛道约束

设计以 2026-08-05 读取的以下官方材料为基准：

- [Agent Infra 官方赛道页面](https://goaihz.com/tracks?track=infra)
- [Agent Infra 参赛手册 PDF](https://oss.goaihz.com/prod/20260720/6e21b053-f18b-4857-83e2-835bd96d5434.pdf)
- [初赛作品提交模板](https://oss.goaihz.com/prod/20260804/2e567d1a-99c1-45ce-8a0f-3d36d11f3314.pptx)

### 10.1 硬性要求

- 至少设计 3 个不同职能 Agent；
- 必须以 AgentTeams 为多 Agent 协同设计基点；
- 需要提交 Agent Identity 清单；
- Skill 是必选项；
- MCP 是推荐项；未使用时需要等价工具集成契约；
- Agent 记忆、知识库 RAG、共享状态、轨迹可观测四项中至少实现两项；
- 高风险动作需要人工确认、审批、回滚和审计边界；
- 必须说明开源依赖、商业服务、模型、数据来源、权限和许可证。

官方八步闭环是：

1. 任务输入；
2. 任务拆解；
3. 上下文传递；
4. 工具调用；
5. 结果验证；
6. 执行证据沉淀；
7. 审批与回滚；
8. 经验沉淀。

### 10.2 评分权重

| 评分项 | 权重 | AgentFit 的设计抓手 |
| --- | ---: | --- |
| 场景价值与行业可复制性 | 25% | 从材料到最小方案的普遍落地问题；项目资产可参数化复用 |
| 多 Agent 协同与自主闭环 | 25% | 五 Agent 职责分离、混合协同、异常分支、审批与回滚 |
| Skill 工程体系与生态复用 | 25% | 元级 Skill、版本、失败处理、安全、跨项目复用和验证 |
| 工程落地、运行验证与安全可审计 | 20% | 真实临时团队、统一试验、故障注入、Trace 和证据包 |
| 开放/开源贡献 | 5% | 可复用 Skill、Schema、模板、示例、文档和接口契约 |

官方明确说明，推荐工具和云产品不按使用数量评分。AgentFit 不应为了展示而堆叠 RAG、MCP、数据库或云产品。

### 10.3 阶段要求

- 初赛截止：2026-08-16；
- 初赛必交：500 字以内作品简介和方案 PPT/PDF；
- 初赛 AgentTeams 代码包可选，但提交时应包含运行入口、依赖、配置、样例输入输出和证据；
- 复赛必须提供可执行 AgentTeams 代码、可运行 Demo、技术文档和验证材料；
- 手册同时把“只有概念/PPT、没有 PoC、实验、仿真、日志、视频或等价材料”列为严重风险，因此 AgentFit 即使初赛代码可选，也应争取形成最小真实运行证据。

### 10.4 当前设计映射

| 官方要求 | 当前设计 |
| --- | --- |
| 至少 3 Agent | AgentFit 常驻五 Agent 元团队 |
| AgentTeams 协同基点 | 常驻元团队和临时候选团队均运行在 AgentTeams 上 |
| Identity | 五个逻辑身份已确认；完整字段未设计 |
| 任务拆解和上下文 | EngagementLead、Project Dossier、Task Envelope 和 Matrix |
| Skill | 确认必须作为核心产品资产；清单未设计 |
| 工具调用 | 通过 Skill/MCP 或等价契约；具体工具未决定 |
| 验证和证据 | 统一任务、故障注入、独立审计和 Trace |
| 审批与回滚 | 试验前、交付前以及成长晋升阶段的人工门禁 |
| 经验沉淀 | 项目交付抽象为版本化资产 |
| 四选二能力 | Project Dossier 和 Trace 已进入架构；正式能力选择仍待确认 |

候选方案可以是无 Agent 或单 Agent，不与比赛的 3 Agent 要求冲突，因为参赛系统本身是五 Agent 的 AgentFit 元团队。

## 11. AgentTeams 复用基线与已知边界

此前本地 v1.1.2 环境已经实际验证：

- Manager 与 Worker 对话；
- 多 Worker 上下文隔离；
- Team Leader 到 Member 的任务委派；
- Human/Team 基础访问隔离；
- MinIO 文件同步；
- Python 代码执行；
- Cron 周期任务及重启后的继续触发；
- Skill 搜索、安装、Worker 级隔离和实际使用。

试用中也观察到过以下边界：

- Team 房间创建存在短暂 Matrix 成员权限竞态，Controller 后续能够恢复；
- Worker 重启后出现过模型 preflight `Connection refused` 警告，但实际任务仍成功执行；
- Matrix 房间与 Agent 访问控制不能直接等同于完整企业 IAM；
- 飞书原生接入和正式试用示例此前没有得到确认；
- v1.2 Beta 的 TeamHarness、WorkerFlow 和部分 Trace 能力不能按稳定能力直接依赖。

**当前建议：** 第一版优先使用已验证的 AgentTeams 稳定能力，只有明确需要且经过验证后才采用 Beta 特性。

**未决定：** AgentFit 实现最终基于 AgentTeams v1.1.2、v1.2 Beta 还是后续稳定版本。

## 12. OpenCode 独立审查记录

在官方手册核验后，使用 OpenCode 1.18.13 和 `zhipuai-coding-plan/glm-5.1` 对项目定义进行过一次独立缺口审查。

审查中有价值的提醒：

- 审批与回滚不能只写在安全说明中，必须进入工作流；
- 经验沉淀需要明确载体和晋升机制；
- 元团队的 Skill 必须证明跨 Agent 或跨项目复用；
- 真实试验、故障注入、可部署工件和否定权是避免退化成咨询聊天机器人的关键。

独立核验纠正了两点：

- GLM 把官方闭环误称为九步，官方手册实际列出八步；
- 多个行业案例有助于证明复用，但不是官方硬性要求。

OpenCode 输出只作为审查意见，不能替代官方条款和工程验证。

## 13. 已确认的设计原则

1. 先定义问题和证据，再生成 Agent 方案；
2. 执行优先于建议，候选方案必须真实试运行；
3. 选择满足要求的最小方案，不以 Agent 数量作为价值；
4. AgentFit 可以否决 Agent 化；
5. Workflow 管状态，通信处理不确定性；
6. 聊天不是正式状态，结构化档案才是；
7. 方案设计、试验执行和结果审计必须分离；
8. 高风险动作必须经过审批并可回滚；
9. 自增长必须经过提案、隔离测试、审计和晋升；
10. 项目交付与可复用资产必须区分；
11. 项目数据必须脱敏后才能进入资产目录；
12. 复用既有模板不能跳过当前项目验证；
13. 不为了比赛堆积无必要 Agent、Skill、MCP、RAG 或云产品；
14. AgentTeams 是真实运行底座，不是只出现在架构图中的名词；
15. 每个结论都应能够追溯到材料证据或运行证据。

## 14. 明确不做或不作为主路线的内容

- 不把 AgentFit 定义为特定职位或特定规模企业的专用产品；
- 不把普通工作流生成作为核心创新；
- 不把 LLM 对候选配置的主观评价称为模拟验证；
- 不用自由群聊替代结构化状态和验收标准；
- 不让新 Agent 或 Skill 未经批准直接进入正式资产；
- 不在设计完成前优先开发 Dashboard 或聊天界面；
- 不重复实现 AgentTeams 已提供的底层基础设施；
- 不把未经验证的 v1.2 Beta 能力写成已具备的稳定能力；
- 不声称市场完全不存在相关方案。

## 16. 推荐的下一项讨论

下一项建议设计以下三个共同基础，并把它们作为一个连续主题讨论：

1. Project Dossier：五个 Agent 共享的项目事实和证据；
2. Task Envelope：Agent 之间委派任务的结构化契约；
3. 项目状态机：从 Intake 到 Learn 的状态转换和审批门禁。

这三项决定后，才能可靠设计 Agent Identity、核心 Skill、自增长触发条件、审计和回放。
