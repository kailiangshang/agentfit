## 一、比赛主题

**Agent 协同在真实场景下的落地：怎么保证可审计、可追溯、可维护、可量化。**

| 保证 | AgentFit 怎么实现 | 骨架对应 |
|---|---|---|
| **可审计** | 训练日志（哈希链保护）记录每轮通过率、损失分布、更新内容、回归结果、λ 变化。任何决策可回溯到具体轮次的具体证据。 | 训练循环第⑨步 |
| **可追溯** | 每个失败样本的损失轨迹自底向上归因到具体层、具体元素、具体原因。归因附带因果性验证（反事实推演）。 | 反向归因算法 |
| **可维护** | 16 个正则指标 + 4 个 λ 权重量化"可维护性"。存在依赖强约束保证无幻影能力、无技术债。部署即生效。 | 正则约束 + 存在依赖 |
| **可量化** | 通过率、成本/样本、人工介入率、回归通过率、各层损失分布——每轮训练后全部产出数字。 | 训练循环第③步 |

## 二、AgentFit 是什么

### 一句话

AgentFit 是一个 **Agent 方案训练系统**：输入业务场景和样本，输出经过多轮训练、通过率验证、边界明确的可部署 Agent 方案。

### 不是什么

| 不是 | 原因 |
|---|---|
| 不是多 Agent 框架 | 不造 Agent 运行时，不管理容器和通信 |
| 不是 AutoML | 不优化模型权重，优化方案架构 |
| 不是观测工具 | 不做 tracing dashboard，用训练日志替代 |
| 不是一次性交付 | 持续训练、持续监控、持续演进 |

### 核心洞察

**方案是"训练出来的"，不是"设计出来的"。**

- 传统：架构师画图 → 评审 → 部署 → 祈祷它能工作
- AgentFit：最简方案起步 → 在真实样本上跑 → 看失败在哪 → 修那一层 → 回归验证 → 迭代到收敛 → 交付

## 三、四层骨架怎么保证四可

### 可审计：训练日志

每轮训练产生一条不可篡改的日志（哈希链保护）：

```json
{
  "epoch": 3,
  "solution_version": 5,
  "pass_rate": 0.85,
  "loss_distribution": {"L1": 0, "L2": 1, "L3": 4, "L4": 0, "human": 5},
  "updates_applied": [
    {"layer": "L3", "element": "refund_routing", "change": "added compound condition", "reason": "3 samples failed on compound refunds"}
  ],
  "regularization": {"L1": 0.0, "L2": 0.12, "L3": 0.08, "L4": 0.0},
  "regression": {"tested": 87, "passed": 87, "rate": 1.0},
  "lambda_changes": [{"param": "λ₃", "from": 0.30, "to": 0.36, "trigger": "L3 coverage > 60% for 2 rounds"}],
  "cost": {"tokens": 1250000, "usd": 2.50},
  "previous_entry_hash": "abc123..."
}
```

任何人拿到训练日志，可以：
- 回答"为什么第 3 轮改了路由规则"（3 个样本在复合退款上失败）
- 回答"这次更新有没有破坏旧功能"（回归 87/87 通过）
- 回答"方案的可维护性怎么样"（L3 正则 0.08，在阈值内）
- 回答"总成本是多少"（3 轮共 $2.50）

### 可追溯：反向归因

每个失败样本产生一条损失轨迹，从 L1 到 L4 逐层检查并验证因果性：

```
样本 #42 失败（复合根因：飞行模式 + 漫游）

L1 检查: toggle_roaming 和 toggle_airplane_mode 都存在 → 跨过
L2 检查: 两个封装都正确 → 跨过
L3 检查: 路由规则只处理了漫游（主因），没处理飞行模式（次因）
  因果性验证: "如果路由先处理飞行模式再处理漫游，样本能通过吗？" → 是
  → 确认根因 = L3（路由规则缺复合条件分支）

附带问题: （无）
```

从失败样本到具体层的具体规则的具体分支，全链路可追溯。

### 可维护：正则约束 + 存在依赖

**正则约束**把"可维护性"从口号变成数字：

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| 原子使用率 > 80% | 一个原子被太多场景依赖 | 改它会影响全局 |
| 链路覆盖度 > 60% | 一条链路承载太多场景 | 万能路由不可维护 |
| Agent 数量 > 5 | 拓扑过于复杂 | 通信开销和调试成本爆炸 |
| 人工介入率 > 30% | 自动化价值低 | 需要重新评估范围 |

**存在依赖**保证没有幻影能力：
- 每个 L4 Agent 追溯到 L3 知识 → L2 工具 → L1 原子 → 基础设施
- 验证函数自动检查所有依赖链，无悬空引用
- 级联变更以原子事务执行，要么全成功要么全回滚

### 可量化：训练指标

每轮训练后自动产出：

| 指标 | 定义 | 交付时报告 |
|---|---|---|
| 通过率 (Pass Rate) | 通过样本数 / 总样本数 | ✅ 核心指标 |
| 写操作准确率 | 正确执行的写操作 / 总写操作 | ✅ |
| 成本/样本 | 每个样本的 token 消耗和美元成本 | ✅ |
| 人工介入率 | 需要人工的样本 / 总样本 | ✅ |
| 回归通过率 | 旧样本在更新后仍通过的比例 | ✅ 必须 100% |
| 各层损失分布 | L1/L2/L3/L4/人工 各占多少失败 | ✅ |
| 正则值 | 各层的可维护性量化 | ✅ |
| 收敛指标 | 通过率变化趋势 | ✅ |

## 四、五种合法交付

训练收敛后，AgentFit 交付以下五种结果之一（全部合法）：

| 结果 | 含义 | 什么时候给 |
|---|---|---|
| 全自动方案 | AI 全权处理 | 通过率 ≥ 阈值、风险可控 |
| 部分自动化 | AI 处理常规、人处理关键 | 大部分能自动，少数需要人 |
| 降级方案 | 简化版，有条件限制 | 预算或能力有限 |
| 保留人工 | 不值得自动化 | 自动化成本 > 人工成本 |
| 拒绝自动化 | 不该用 AI | 通过率太低、风险太大 |

**"不自动化"和"自动化"一样是合法结论。**
