## 一、四层定义

```
正向执行方向（自顶向下）                    反向归因方向（自底向上）
─────────────────────                    ─────────────────────
                                         ④ 拓扑适配吗？
L4  行为拓扑层                            L4  行为拓扑层
    Agent 架构 + 协作模式                  ← 最后检查
    + 行为序列 + 人工介入位置
        ↓ 调用                                  ↑ 归因
L3  可复用知识层                            L3  可复用知识层
    Skill + 路由规则 + 排查链                ← 先查有无链路
    + 决策阈值 + 经验记录                     再查链路分支是否正确
        ↓ 调用                                  ↑ 归因
L2  可二次开发能力层                        L2  可二次开发能力层
    对 Solid 的安全封装 + 组合               ← 先查有无封装
    + 口径统一 + 送审路由                     再查封装逻辑是否正确
        ↓ 调用                                  ↑ 归因
L1  Solid 层                              L1  Solid 层
    固定可用的原子能力                       ← 最先检查
    API + 数据库 + 知识库                    有没有这个原子？
    + 外部系统 + 人工审核                    没有就直接停下，加原子
```

### L1 · Solid 层（固定地基）

**固定可用的、不可二次开发的原子能力。**

- 每个 Solid 原子就是一个"能做的事"，不需要拆解、不需要组合、拿起来就能用
- **人工审核是 L1 的标准原子**，和 `query_database` 同级，不是外挂

```
human_review 是 L1 的标准原子:

输入:
  question:   "需要人判断的问题"
  context:    "相关背景信息"
  options:    "可选的决策路径"
  domain:     "领域标签" → 决定 L2 怎么路由

输出:
  decision:   "approve / reject / escalate / modify"
  reason:     "判断理由"
  conditions: "附加条件"
```

层内约束：
- 只增不删（删除需走完整变更流程）
- 不可二次开发（封装是 L2 的事）
- 由基础设施团队维护

### L2 · 可二次开发能力层

**对 Solid 层原子的安全封装和组合。**

封装类型：
| 类型 | 做什么 | 例子 |
|---|---|---|
| 安全包装 | 加鉴权、前置检查、后置日志 | `safe_create_refund`: 验证身份→检查金额→超限送审 |
| 组合能力 | 串多个 L1 原子为一个单元 | `full_diagnostic`: 查设备+查网络+查账户→综合诊断 |
| 口径封装 | 统一计算/聚合方式 | `calculate_refund_amount`: 按政策计算（含优惠券） |
| 送审路由 | 决定人工审核送给谁 | 金额>$100→财务；安全→安全团队 |

层内约束：
- 必须通过 L2 才能触达 L1（L3/L4 不能绕过）
- 一个 L2 可以封装多个 L1
- L2 之间禁止互相调用（需要组合 → 上提到 L3 用 Skill/排查链组合）

### L3 · 可复用知识层

**一切可复用的方法论、经验和知识。**

五种知识类型的严格区分：

| 概念 | 定义 | 创建方式 | 更新方式 | 正则约束 |
|---|---|---|---|---|
| **Skill** | 可复用的操作序列模板（"怎么做某类事"） | 初始构建时创建；训练中按需新增 | 训练中修改步骤或参数 | 复用率 |
| **路由规则** | IF-THEN 条件判断（"什么情况走哪条路"） | 初始从样本归纳；训练中新增分支 | 归因驱动修正 | 覆盖度、分支因子 |
| **排查链** | 有序的诊断-修复-验证步骤序列 | 初始从解决轨迹归纳 | 归因驱动增减步骤 | 链路长度 |
| **决策阈值** | 数值化判断边界（"重试超 N 次升级"） | 初始配置 | 归因驱动调整 | 少量，无强约束 |
| **经验记录** | 从失败中学到的教训 | 训练中从损失轨迹归纳 | 活跃→归档（不物理删除，过时标记 superseded） | 去重度、引用率 |

经验记录的治理策略：
- 去重：新教训与已有教训语义相似度 > 90% → 合并
- 过时：对应链路已重构 → 标记为 superseded
- 上限：训练期间最多 200 条活跃教训
- 压缩：超上限时按引用频率淘汰 bottom 10%

层内约束：
- 只能通过 L2 使用能力（知识决定怎么走，走要靠工具）
- 知识之间禁止执行时互调（一个 Skill 不能在自己步骤中调用另一个 Skill，一条排查链不能跳转到另一条排查链，一条经验记录不能以另一条经验记录作为判断依据）
- 路由规则对 Skill/排查链的调度关系（IF X THEN 走 Skill A）是 L3 的组织职能，不视为互引
- 知识有版本（旧版本保留可回滚）

### L4 · 行为拓扑层

**Agent 的整体架构和行为组织。** 不只是 DAG。

拓扑要素：
| 要素 | 做什么 | 例子 |
|---|---|---|
| Agent 数量 | 几个独立决策体 | 1 个 / 2 个 / N 个 |
| 协作模式 | Agent 间怎么交互 | 串行 / 并行 / 层级 / 讨论 |
| 行为序列 | 整体处理流程 | 接收→诊断→分支{自动修复\|人工审核}→验证→输出 |
| 人工介入位置 | 在哪些节点人参与 | 决策点（审批）/ 执行点（共同操作）/ 终点（验收） |
| 升级路径 | 处理不了怎么办 | 转人工 / 降级 / 拒绝 |

层内约束：
- L4 是架构决策，改变拓扑影响全局
- 必须基于证据（训练数据显示当前架构处理不了某类问题才改）
- Simple First：初始从最简开始（单 Agent），失败证据驱动复杂化

### 跨层依赖铁律（纵向）

```
L4 → 只能调 L3
L3 → 只能调 L2
L2 → 只能调 L1
```

唯一例外：L4 可直接调 L2 的人工审批工具（`human_review` 封装），但受三条防护栏约束（见下）。

#### L4 直调 L2 例外的防护栏

```
L4 可直接调用 L2 的 human_review 工具，但仅限以下条件同时满足:

① 仅限 human_review 工具
   L4 不能直调 L2 的任何其他工具（如 safe_create_refund 等）
   human_review 是特殊的：人工介入是架构级决策，不是知识级判断

② 必须在 L3 登记触发条件
   L3 必须有一条路由规则或排查链步骤
   声明"什么情况下触发此人工审批"
   否则 L4 的直调没有依据，验证不通过

③ 归因走特殊路径
   如果 human_review 相关的样本失败
   归因时先查 L3 的触发条件是否正确
   再查 L2 的送审路由是否正确
   不跳过 L3 直接归因给 L2
```

### 同层约束（横向铁律）

| 层 | 同层引用 | 理由 |
|---|---|---|
| L1 | ❌ 禁止 | 原子之间无依赖。每个原子独立可用。A 调 B → A 不是真正的原子 |
| L2 | ❌ 禁止 | 工具之间无调用。需要组合 → 上提到 L3 用 Skill/排查链组合 |
| L3 | ❌ 禁止执行时互调 | Skill 步骤调另一个 Skill / 排查链跳转另一条链 / 经验引用经验。路由规则→Skill 是调度（组织职能），不算互引 |
| L4 | ✅ 允许（受约束） | Agent 间通信是拓扑的定义本身（拓扑 = 节点 + 边），但须满足三条约束 |

#### L4 同层通信的三条约束

```
① 通信必须沿拓扑定义的边进行
   合法: L4 定义了 "Agent A → Agent B" 的边，A 通过这条边向 B 传递结果
   非法: L4 没有定义 A→C 的边，但 A 在运行时直接调用 C
   拓扑是静态定义的。运行时通信只能在已定义的边上发生。
   需要新通信路径 → 修改拓扑 → 触发 L4 变更（需证据支撑）

② 通信内容是 L3 层面的
   合法: Agent A 完成诊断，将诊断结论（L3 产物）传给 Agent B 执行
   非法: Agent A 直接调用 Agent B 内部的 safe_create_refund（L2 工具）

③ 不允许绕过拓扑的隐式通信
   Agent 之间不能通过共享内存、全局变量、文件系统等方式绕过拓扑边通信
   所有 Agent 间信息流必须在拓扑中有对应的边
```

### 存在依赖强约束（全链路逐层支撑）

**任何一层声明一个能力，下层必须已经提供支撑。不能凭空创造。**

```
L4 声明"我有诊断 Agent"
  ↓ 这句话要成立，L3 必须已有
L3 存在"诊断排查链和路由规则"
  ↓ 这句话要成立，L2 必须已有
L2 存在"safe_get_device_state 等诊断工具"
  ↓ 这句话要成立，L1 必须已有
L1 存在"get_device_state 原子"
  ↓ 这句话要成立，基础设施必须已有
基础设施存在"设备管理系统 API"
```

**每一层的每个能力，都必须能一路追溯到物理基础设施。**

#### 具体例子

| 层 | 声明 | 下层必须已有什么 | 如果没有 |
|---|---|---|---|
| L4: "我有诊断 Agent" | Agent 使用诊断知识 | L3 必须有诊断排查链 | 不能建这个 Agent，先建 L3 |
| L3: "我有经验记录" | 知识层能查历史经验 | L2 必须有 `safe_memory_search` 工具 | 不能声明有经验，先建 L2 工具 |
| L3: "IF 退款 THEN safe_create_refund" | 路由规则引用工具 | L2 必须有 `safe_create_refund` 工具 | 不能建这条路由，先建 L2 封装 |
| L2: "我有 safe_memory_search" | 工具封装原子 | L1 必须有 `memory_search` 原子 | 不能建这个工具，先建 L1 原子 |
| L2: "我有 safe_finance_review" | 工具封装人工审核 | L1 必须有 `human_review` 原子 | 不能建这个工具，先建 L1 人工原子 |
| L1: "我有 memory_search 原子" | 原子接口真实系统 | 基础设施必须有存储后端（DB/文件/云端） | 不能建这个原子，先建基础设施 |

#### 构建顺序（强制自底向上）

```
正确顺序:
  ① 确认基础设施存在（API、数据库、存储、人工团队）
  ② 在 L1 注册原子（每个原子对准一个真实基础设施）
  ③ 在 L2 封装工具（每个工具只封装已存在的 L1 原子）
  ④ 在 L3 创建知识（每条规则/链路只引用已存在的 L2 工具）
  ⑤ 在 L4 设计拓扑（每个 Agent 只使用已存在的 L3 知识）

禁止:
  ✗ 在 L1 没有原子的情况下建 L2 工具
  ✗ 在 L2 没有工具的情况下建 L3 路由规则
  ✗ 在 L3 没有知识的情况下建 L4 Agent 角色
  ✗ 在基础设施没有后端的情况下建 L1 原子
```

#### 更新时的级联检查与原子性

训练中发现"需要新能力"时，不能直接在目标层创建——必须先检查下层是否支撑，如果下层缺失，更新目标下移。**级联变更是原子操作：要么全部层一次性更新成功，要么全部回滚。**

```
级联更新流程:

训练发现: 样本失败因为缺少"经验回溯"能力
归因: L3 缺少经验路由规则
  ↓ 级联检查（存在依赖强约束）
L3 经验路由 需要 L2 的 safe_memory_search
  → L2 没有这个工具 → 更新目标下移到 L2
    ↓ 继续检查
L2 safe_memory_search 需要 L1 的 memory_search 原子
  → L1 没有这个原子 → 更新目标下移到 L1
    ↓ 继续检查
L1 memory_search 原子需要存储基础设施
  → 基础设施没有 → 这不是 AgentFit 能自己解决的
  → 升级给用户: "需要你提供一个存储系统（可以是 SQLite/文件/云服务）"
```

#### ChangeTransaction（级联变更的原子性保障）

```
当一次更新建议涉及多层时（如 L1+L2+L3 同时新增），必须作为一个原子事务执行:

ChangeTransaction:
  proposed_changes: [
    {layer: "L1", action: "add_atom", target: "memory_search", ...},
    {layer: "L2", action: "add_tool", target: "safe_memory_search", wraps: "memory_search", ...},
    {layer: "L3", action: "add_knowledge", target: "experience_routing", references: "safe_memory_search", ...}
  ]

执行流程:
  ① BEGIN: 记录当前方案版本快照
  ② 按自底向上顺序应用所有变更（L1 → L2 → L3 → L4）
  ③ 验证: 运行 validate_existence_dependencies(solution)
     → 通过 → COMMIT: 变更生效，方案版本号 +1
     → 失败 → ROLLBACK: 恢复到步骤 ① 的快照，报告失败原因

禁止:
  ✗ 只应用 L1 而不应用 L2/L3（中间状态方案不允许存在）
  ✗ 先应用 L3 再回头补 L1/L2（违反自底向上顺序）
  ✗ 部分成功部分失败时保留成功部分（必须全成功或全回滚）
```

级联更新顺序（必须从底往上，且原子性执行）:
  ① 用户确认基础设施（如果需要新基础设施）
  ② AgentFit 以 ChangeTransaction 形式执行: L1 → L2 → L3 → L4
  ③ 验证通过后 COMMIT，方案版本号递增

#### 验证规则（每次方案变更后执行）

```python
def validate_existence_dependencies(solution):
    """验证所有层间依赖完整 + 同层约束 + L4 通信合法性。"""

    errors = []

    # ── 纵向: L1 → 基础设施 ──
    for atom in solution.L1_atoms:
        if not infrastructure_exists(atom.backend):
            errors.append(f"L1 原子 {atom.id} 引用了不存在的基础设施 {atom.backend}")

    # ── 纵向: L2 → L1 ──
    for tool in solution.L2_tools:
        for wrapped_atom in tool.wraps:
            if wrapped_atom not in solution.L1_atoms:
                errors.append(f"L2 工具 {tool.id} 封装了不存在的 L1 原子 {wrapped_atom}")

    # ── 纵向: L3 → L2 ──
    for knowledge in solution.L3_knowledge:
        for referenced_tool in knowledge.references:
            if referenced_tool not in solution.L2_tools:
                errors.append(f"L3 知识 {knowledge.id} 引用了不存在的 L2 工具 {referenced_tool}")

    # ── 纵向: L4 → L3 ──
    for element in solution.L4_topology:
        for used_knowledge in element.uses:
            if used_knowledge not in solution.L3_knowledge:
                errors.append(f"L4 元素 {element.id} 使用了不存在的 L3 知识 {used_knowledge}")

    # ── 横向: L2 同层互调禁止 ──
    for tool in solution.L2_tools:
        if hasattr(tool, 'references'):
            for ref in tool.references:
                if ref in solution.L2_tools:
                    errors.append(f"L2 工具 {tool.id} 引用了同层工具 {ref}，违反同层约束")

    # ── 横向: L3 执行时互调禁止（调度不算）──
    # 路由规则 references Skill/Chain = 调度（合法）
    # Skill 步骤 calls 另一个 Skill = 执行时互调（违规）
    for knowledge in solution.L3_knowledge:
        if knowledge.type == "skill" or knowledge.type == "chain":
            # 检查 Skill/Chain 的执行步骤是否引用了同层知识
            for step in knowledge.steps:
                if hasattr(step, 'calls_knowledge') and step.calls_knowledge:
                    if step.calls_knowledge in solution.L3_knowledge:
                        errors.append(
                            f"L3 {knowledge.type} {knowledge.id} 的步骤 {step.id} "
                            f"执行时调用了同层知识 {step.calls_knowledge}，违反同层约束"
                        )
        elif knowledge.type == "experience_record":
            # 经验记录不能以另一条经验为判断依据
            if hasattr(knowledge, 'based_on') and knowledge.based_on:
                if knowledge.based_on in solution.L3_knowledge:
                    errors.append(
                        f"L3 经验记录 {knowledge.id} 以同层经验 {knowledge.based_on} 为判断依据，"
                        f"违反同层约束"
                    )
        # 路由规则 references Skill/Chain = 调度 → 不检查，合法

    # ── 横向: L4 同层通信合法性 ──
    for edge in solution.L4_topology.edges:
        # 约束 ①: 每条通信边必须在拓扑定义中显式声明
        if edge not in solution.L4_topology.declared_edges:
            errors.append(f"L4 存在未声明的通信边 {edge}")

        # 约束 ②: 边上流动的内容必须是 L3 层产物
        if edge.payload_type not in ("L3_decision", "L3_diagnosis",
                                      "L3_route_result", "L3_skill_output"):
            errors.append(f"L4 边 {edge} 传递了非 L3 层内容: {edge.payload_type}")

    # ── 例外防护栏: L4 直调 L2 仅限 human_review ──
    for element in solution.L4_topology:
        if hasattr(element, 'direct_L2_calls'):
            for call in element.direct_L2_calls:
                if call.target_tool != "human_review":
                    errors.append(
                        f"L4 元素 {element.id} 直调了非 human_review 的 L2 工具 {call.target_tool}"
                    )
                # 防护栏②: 必须在 L3 有触发条件登记
                trigger_registered = any(
                    k.id == call.trigger_knowledge
                    for k in solution.L3_knowledge
                )
                if not trigger_registered:
                    errors.append(
                        f"L4 元素 {element.id} 直调 human_review 但未在 L3 登记触发条件"
                    )

    return errors  # 空列表 = 验证通过
```

#### 这个约束保证了什么

| 保证 | 含义 |
|---|---|
| **无幻影能力** | 不能声明一个没有实现支撑的功能 |
| **全链路可追溯** | 每个能力从 L4 到基础设施都能追到底 |
| **天然可维护** | 改某层的东西，影响范围清晰（只影响直接上层） |
| **无技术债** | 不存在"先声明后实现"的欠账 |
| **部署即生效** | 因为一切都是实在的，方案生成即可部署 |

## 二、反向归因算法

### 核心原则

| 原则 | 含义 |
|---|---|
| **自底向上** | 从 L1 开始逐层检查，不跳层 |
| **找到即验证** | 发现异常后，验证是否为根因（因果性校验），不能"找到即停" |
| **附带问题不阻塞** | 发现但不构成根因的异常记录为附带问题，继续往上查 |
| **就近归因** | 问题出在哪层就归因给哪层，不往上推 |

### 完整算法

```
样本执行失败
  ↓
从 L1 开始逐层检查:

Step 1 → 检查 L1（Solid 层）
  "这个样本的解决需要哪些原子？L1 里有没有？"
  ├── 缺少原子
  │     验证因果性: "如果这个原子存在，样本能通过吗？"
  │     ├── 是 → 确认根因 = L1（缺原子），停止
  │     └── 否 → 标记附带问题，继续往上
  └── 原子都有 → 继续往上

Step 2 → 检查 L2（能力层）
  "这些原子有没有被正确封装？"
  ├── 没有封装
  │     验证因果性: "如果有了封装，样本能通过吗？"
  │     ├── 是 → 确认根因 = L2（缺封装），停止
  │     └── 否 → 标记附带问题，继续往上
  ├── 封装存在但逻辑错误
  │     验证因果性: "这个错误在关键路径上吗？"
  │     方法: 检查该异常是否影响后续步骤的输入
  │     ├── 在关键路径上 → 确认根因 = L2（封装错误），停止
  │     └── 不在关键路径上（如日志格式问题）→
  │         标记附带问题（记录但不停止），继续往上
  └── 封装正确 → 继续往上

Step 3 → 检查 L3（知识层）
  "有没有一条知识链路覆盖这个场景？"
  ├── 没有链路
  │     验证因果性: "如果有这条链路，样本能通过吗？"
  │     ├── 是 → 确认根因 = L3（缺链路），停止
  │     └── 否 → 标记附带问题，继续往上
  ├── 有链路但走错分支
  │     验证因果性: "如果路由到正确分支，样本能通过吗？"
  │     ├── 是 → 确认根因 = L3（路由错误），停止
  │     └── 否 → 标记附带问题，继续往上
  └── 链路正确 → 继续往上

Step 4 → 检查 L4（拓扑层）
  "当前架构适合这类问题吗？"
  ├── 不适合（如单 Agent 处理不了复合问题）
  │     确认根因 = L4（架构不匹配），停止
  └── 适合 →
        前置检查: 这个失败样本是否真的需要 AI？
        判定依据（按优先级）:
        ① 样本的期望操作是否包含 human_review 原子
           → 是 → 归因为"需要人工"（不是 AI 的失败）
        ② 样本的期望操作是否涉及主观判断（金额争议/情绪安抚/政策模糊）
           → 是 → 归因为"需要人工"
        ③ 样本的期望操作是否使用了 L1 中不存在的原子
           → 是 → 这是 L1 损失（回到 Step 1，归因器漏检了）
        ④ 排除以上三种 → 归因为"评价标准可能有误"
           → 人工审查评价规则本身是否合理

附带问题处理:
  所有在检查过程中发现但不构成根因的异常
  → 记录到附带问题清单
  → 在聚合分析阶段统一报告
  → 不阻塞当前层的归因
  → 在后续训练中可能升级为根因（当主因被修复后浮现）
```

### 因果性验证（反事实推演）

```python
def is_root_cause(anomaly, execution_trace, expected_outcome):
    """判断发现的异常是否是失败的直接原因。"""

    anomalous_step = find_step_containing(execution_trace, anomaly)

    if anomalous_step is None:
        return False  # 异常不在执行轨迹中

    # 检查该步骤是否在关键路径上
    # 关键路径 = 该步骤的输出被后续步骤使用，且影响最终结果
    downstream_steps = get_downstream(execution_trace, anomalous_step)

    if not downstream_steps:
        return False  # 无下游依赖 → 旁路操作（如日志）→ 附带问题

    for step in downstream_steps:
        if step.depends_on(anomalous_step.output):
            if would_change_outcome(anomalous_step, step, expected_outcome):
                return True  # 下游依赖且影响结果 → 可能是根因

    return False

def would_change_outcome(anomalous_step, dependent_step, expected):
    """反事实：如果异常被修复，依赖步骤的输出会不同吗？"""
    actual_output = anomalous_step.output
    expected_output = anomalous_step.expected_output
    if actual_output == expected_output:
        return False  # 输出实际相同，异常无影响
    return True  # 输出不同 → 下游行为会变 → 可能是根因
```

## 三、每层正则约束

### 设计原则

正则约束防止"单点耦合爆炸"——某个原子/工具/链路/Agent 承载了太多职责，表面通过率高，实际维护成本爆炸。类比 ML 中的过拟合：一个神经元做了所有事 → 训练集好 → 新样本崩溃。

### 正则指标的操作定义

每个指标定义为三元组：**(数据源, 计算时机, 计算者)**

#### 结构性正则（静态分析，方案更新后计算）

| 指标 | 层 | 阈值 | 数据源 | 计算时机 | 计算者 | 算法 |
|---|---|---|---|---|---|---|
| 原子使用率 | L1 | > 80% = 过度耦合 | L3 链路对 L1 原子的引用关系 | 方案更新后 | 方案验证器 | 遍历 L3 链路→统计每个 L1 原子被引用次数→max/total |
| 原子稀缺率 | L1 | > 30% = 冗余 | 同上 | 方案更新后 | 方案验证器 | 使用率 < 5% 的原子数 / 总原子数 |
| 封装复杂度 | L2 | > 5 个 L1 原子 = 太复杂 | 每个 L2 工具的 wraps 列表 | 方案更新后 | 方案验证器 | 遍历 L2 工具→统计封装的 L1 原子数 |
| 工具复用率 | L2 | < 2 条链路引用 = 低复用 | L3 链路对 L2 工具的引用关系 | 方案更新后 | 方案验证器 | 遍历 L3 链路→统计每个 L2 被引用次数 |
| 链路长度 | L3 | > 10 步 = 太长 | 每条 L3 链路的步骤数 | 方案更新后 | 方案验证器 | 遍历 L3 链路→统计步骤数 |
| 分支因子 | L3 | > 15 个 = 太复杂 | 每条 L3 链路的条件分支数 | 方案更新后 | 方案验证器 | 遍历 L3 链路→统计 if/else 分支数 |
| Agent 数量 | L4 | > 5 个 = 需要理由 | L4 拓扑定义 | 方案更新后 | 方案验证器 | 直接读取 |

#### 行为性正则（动态统计，每轮训练后从执行轨迹计算）

| 指标 | 层 | 阈值 | 数据源 | 计算时机 | 计算者 | 算法 |
|---|---|---|---|---|---|---|
| 原子增长率 | L1 | > 5 个/轮 = 过快 | 方案版本间 diff | 每轮训练后 | 归因器 | 本轮新增原子数 |
| 审批延迟 | L2 | > 5min = 瓶颈 | 执行轨迹中 human_review 步骤的时间戳 | 实时 | 监控协程 | 滑动平均 |
| 链路覆盖度 | L3 | > 60% = 过度集中 | 当前批次全部执行轨迹 | 每轮训练后 | 归因器 | 每条链路被触发次数/总样本数 |
| 知识冲突率 | L3 | > 5% = 需要治理 | 当前批次中多条链路矛盾判断的样本 | 每轮训练后 | 归因器 | 同一输入被不同链路路由到不同输出 |
| 经验去重度 | L3 | > 20% 重复 = 归纳有问题 | 新教训 vs 已有教训的语义相似度 | 每轮训练后 | 归因器 | 相似度 > 90% 的新教训数 / 新教训总数 |
| 经验引用率 | L3 | > 30% 未被引用 = 冗余 | 活跃教训 vs L3 链路引用关系 | 方案更新后 | 方案验证器 | 未被引用的活跃教训 / 总活跃教训 |
| 人工介入率 | L4 | > 30% = 自动化价值低 | 当前批次全部执行轨迹 | 每轮训练后 | 归因器 | 含 human_review 步骤的样本 / 总样本 |
| 通信开销 | L4 | > 10 轮/样本 = 太多 | 当前批次全部执行轨迹 | 每轮训练后 | 归因器 | Agent 间消息轮次（多 Agent 场景） |
| 拓扑变更频率 | L4 | > 1 次/轮 = 不稳定 | 方案版本间 diff | 每轮训练后 | 归因器 | 本轮拓扑改动次数 |

## 四、λ 调节的两级闭环

### 总损失函数

```
总损失 = 任务损失 + λ₁·L1正则 + λ₂·L2正则 + λ₃·L3正则 + λ₄·L4正则

其中:
  任务损失 = 1 - 通过率
  λ₁~λ₄ = 正则权重（控制"通过率 vs 可维护性"的平衡）
```

### 每层正则项的聚合公式

每层的正则项值 = 该层最严重违规指标的超阈比例（hinge loss 形式，不用亚系数）：

```
Lx正则 = max(0, worst_violation_ratio)

其中:
  worst_violation_ratio = 该层所有正则指标中，
                          actual_value / threshold_value 的最大值 - 1

当 actual ≤ threshold 时，该指标贡献为 0（不违规）
当 actual > threshold 时，贡献为超出比例

示例:
  L3 有 5 个正则指标:
    链路覆盖度: 实际 65% / 阈值 60% → 超出 8.3%
    链路长度:   实际 8 步 / 阈值 10 步 → 未超 → 0
    分支因子:   实际 12 个 / 阈值 15 个 → 未超 → 0
    知识冲突率: 实际 3% / 阈值 5% → 未超 → 0
    经验去重度: 实际 10% / 阈值 20% → 未超 → 0

  L3正则 = max(0, 65/60 - 1) = 0.083

简洁: 4 个超参（λ₁~λ₄），16 个指标通过 max 聚合为一层一个值
```

### 默认权重

| 权重 | 默认值 | 含义 | 调大 | 调小 |
|---|---:|---|---|---|
| λ₁ | 0.1 | 原子层耦合惩罚 | 更多个简单原子 | 允许大而全原子 |
| λ₂ | 0.2 | 工具层复杂度惩罚 | 更简单封装 | 允许复杂工具 |
| λ₃ | 0.3 | 知识层集中度惩罚 | 更多专门链路 | 允许万能路由 |
| λ₄ | 0.4 | 拓扑复杂度惩罚 | 更少 Agent | 允许多 Agent |

**λ₄ > λ₃ > λ₂ > λ₁**：越上层过度复杂越危险（影响全局），惩罚越重。

### Level 1: 自动微调（无需人审）

```
范围: 单个 λ 变化 ≤ ±20%
触发: 对应层正则项连续 2 轮超过阈值
动作: 训练循环控制器自动调整
限制: 每轮最多调 1 个 λ；累计变化不超初始值 ±50%
日志: 记录到训练日志

示例:
  Round 5: L3 链路覆盖度 = 65%（阈值 60%）→ 未触发
  Round 6: L3 链路覆盖度 = 68% → 连续 2 轮 → 触发
  动作: λ₃ 自动 × 1.2（0.3 → 0.36）
  日志: "λ₃ adjusted 0.3 → 0.36, trigger: L3 coverage > 60% for 2 rounds"
```

### Level 2: 建议调整（需人审）

```
范围: 单个 λ 变化 > ±20%，或多个 λ 同时调整
触发:
  a) 通过率与正则项明确对抗（一个升另一个必降）
  b) Level 1 微调累计达上限但问题未解决
  c) 用户主动询问

动作: 生成结构化建议，进入人审队列

建议格式:
  {
    "type": "λ_adjustment_suggestion",
    "trigger": "pass_rate_92%_but_L2_reg_3x_over",
    "current": {"λ₂": 0.2, "L2_reg": 0.61},
    "suggested": {"λ₂": 0.4},
    "expected_impact": "pass_rate 92% → ~88%, L2_reg 0.61 → ~0.25",
    "trade_off": "牺牲 4% 通过率换取更简单的工具封装",
    "user_response_deadline": "下一轮训练前"
  }

用户不响应: 用当前值继续（不自动应用 Level 2 建议）
用户接受: 立即应用，记录日志
用户拒绝: 保留当前值，相同触发 3 轮内不再重复建议
```

### 闭环流程图

```
                ┌─────────────────────────────┐
                │      训练循环控制器           │
                └───────────┬─────────────────┘
                            │
                ┌───────────▼─────────────────┐
                │   每轮结束后计算正则项         │
                │   (归因器 + 方案验证器)       │
                └───────────┬─────────────────┘
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
正则项 ≤ 阈值       正则项 > 阈值       正则项对抗通过率
          │           连续 2 轮              │
          │                 │                 │
┌────────▼────┐  ┌────────▼────────┐  ┌────▼─────────────┐
│  无需调整    │  │  Level 1 微调   │  │  Level 2 建议    │
│  继续训练    │  │  自动 ±20%     │  │  人审后应用      │
└─────────────┘  │  记录日志       │  │  不响应=不应用   │
                 └────────────────┘  └──────────────────┘
```

### 用户调整场景

| 用户情况 | 建议 | 理由 |
|---|---|---|
| 团队小（<5人），维护能力有限 | λ 全部 ×2 | 宁可通过率低也要方案简单 |
| 团队大，有专门工具团队 | λ₂ 调小 | 允许复杂封装 |
| 场景简单（线性为主） | λ₄ 保持或调大 | 不需要多 Agent |
| 场景复杂（多域交叉） | λ₄ 调小 | 允许灵活拓扑 |
| 合规严格 | λ₂ 调大 | 封装要简单透明便于审计 |
| 追求极致通过率 | λ 全部调小 | 允许过拟合换通过率 |

## 五、L3 经验记录的层内维护

经验记录（Memory）是 L3 知识的一种，不单独提取为独立系统。它在训练和运行期间都作为 L3 的一部分存在，增长和清理是 L3 层内的治理策略。

### 训练期间

```
来源: 失败样本 → 归因 → 提取教训
上限: 200 条活跃教训（层内约束）
治理: 去重(相似度>90%合并) / 过时标记(链路重构→superseded) / 压缩(按引用频率淘汰)
```

### 运行期间

```
经验记录继续作为 L3 的一部分:
  - 新经验从运行中的新模式归纳（触发重训练时进入）
  - 过时经验随链路重构自动标记
  - 膨胀治理纳入 L3 正则（经验去重度、经验引用率）
  - 运行日志（原始执行记录）存储在 L3 之外的运行系统，不混入知识层
```

**Memory 就是 L3 的经验记录，没有独立的 Memory 系统。**

## 七、完整训练循环（汇总）

```
初始化:
  用户提供材料+样本+评价方式
  AgentFit 构建 L1-L4 初始方案

Loop:
  ① 前向: 取一批样本，用当前方案执行
  ② 损失: 对每个失败样本，自底向上(L1→L4)归因
          每层做因果性验证（找到即验证，不是找到即停）
          附带问题记录但不阻塞归因
  ③ 聚合: 统计各层损失模式 + 计算正则项
          结构性正则(方案验证器) + 行为性正则(归因器)
  ④ 反向: 生成分层更新建议（考虑正则约束）
  ⑤ λ调节: Level 1 自动微调(≤±20%) 或 Level 2 建议(>±20%需人审)
  ⑥ 人审: 用户审核更新建议
  ⑦ 应用: 更新对应层
  ⑧ 回归: 旧样本重跑，确认不遗忘
  ⑨ 日志: 训练日志追加（通过率/损失分布/更新/回归/λ变化）

收敛条件:
  - 通过率连续 N 轮无显著提升
  - 剩余失败全部归因于"需要人工"
  - 预算/时间/复杂度超限
  - 回归池通过率下降（出现遗忘，需回滚）

交付:
  - 可部署方案包 + 训练记录 + 适用边界 + 持续监控配置
```
