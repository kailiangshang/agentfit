## 1. 执行摘要

AgentFit 是一支运行在 AgentTeams 上的 Agent 解决方案元团队。它从业务材料、流程、问题和历史案例出发，将用户要解决的问题编译为任务语义，将现有 Agent、Skill、MCP、工具、记忆、通信和人工能力编译为能力语义，在统一能力图中搜索、试运行并评估候选架构，最终交付满足验收约束的最小充分方案，或者有证据地否决不适合的自动化方案。

AgentFit 不试图成为另一套通用 Agent 框架。AgentTeams 提供身份、通信、运行和团队协同底座；AgentFit 提供的是业务问题与 Agent 基础设施之间缺失的方案工程方法：

```text
理解业务
→ 编译任务语义与能力语义
→ 构造基础能力图
→ 划分 Agent 边界和共享范围
→ 生成不同复杂度的候选
→ 真实试运行和独立评测
→ 选择、降级或否决
→ 交付并沉淀跨项目经验
```

AgentFit 的核心命题是：

1. 任务语义定义“什么结果算好”；
2. 能力语义定义“可以拿什么进行搜索”；
3. Agent 是被赋予独立决策与责任边界的可执行子图，而不是普通能力节点；
4. Agent 架构设计是能力图搜索、Agent 分区搜索、参数搜索和共享范围搜索的联合优化；
5. 项目内通过内外双循环寻找最小充分架构，跨项目通过 Meta-learning 更新搜索先验；
6. 合法结果包括 Agentless、单 Agent、多 Agent、部分自动化以及拒绝自动化。
7. LLM 只是实现上述方法的一类能力算子；语义编码、对齐、分解、搜索和更新可以由规则、Embedding、矩阵分解、图算法、优化算法、人工或其组合完成。

## 2. 问题定义

### 2.1 市场断层

现有 Agent 方案通常落在两个极端：

- 重型平台提供大量能力，但要求使用者理解和部署许多与当前场景无关的组件；
- 轻型框架足够灵活，但要求使用者自己理解业务、设计 Agent、开发工具和建立评测。

两者通常都隐含一个前提：使用者已经知道自己应该构建什么。真实项目却往往只有业务材料、流程、问题、历史案例和若干现有系统，尚不清楚：

- 是否应该使用 Agent；
- 需要固定 Workflow、单 Agent还是多 Agent；
- 需要哪些 Skill、MCP、Memory 和通信能力；
- 哪些能力应该私有或共享；
- 增加的复杂度是否产生足够价值；
- 方案如何验证、审计、回滚和持续演进。

AgentFit 解决的不是“如何再运行一个 Agent”，而是“如何从真实问题出发，得到一个有证据支持的可部署 Agent 方案”。

### 2.2 场景边界，而非用户边界

AgentFit 不以企业规模、行业、岗位或用户身份限定适用范围。一个场景适合使用该方法，通常需要满足以下条件：

1. 存在一类重复出现的任务，而非纯一次性问题；
2. 输入、输出和失败结果能够描述；
3. 存在案例、规则、运行反馈或其他可核验事实；
4. 结果能够通过测试、证据、人工复核或业务指标验证；
5. 存在质量、成本、时延、安全或自动化率之间的权衡；
6. 必要工具和系统能够在受控权限下访问；
7. 可以设置预算、沙箱、审批、降级或回滚；
8. 确实存在不同复杂度的候选方案可供比较。

如果任务没有可描述的验收标准、没有足够证据，或者最终责任无法安全转移，AgentFit 应输出部分自动化、人工保留或拒绝自动化，而不是强行生成多 Agent 方案。

## 3. 总体架构

### 3.1 两层结构

AgentFit 采用两层结构：

1. **常驻元团队**：理解业务、建模、搜索、试验、审计和交付；
2. **临时候选系统**：由元团队创建，在隔离环境中接受统一任务与评测，完成后被选择、修改或销毁。

Preflight Lab 是元团队用于部署候选、注入任务、运行故障试验和收集证据的实验环境，不是独立产品。

```text
用户与业务材料
       │
       ▼
┌──────────────── AgentFit 常驻元团队 ────────────────┐
│ 语义编译 → 候选设计 → 试验控制 → 独立审计 → 交付   │
└──────────────────────┬──────────────────────────────┘
                       │ 创建、运行、比较、销毁
                       ▼
          ┌──────── Preflight Lab ────────┐
          │ 候选 A：固定 Workflow         │
          │ 候选 B：单 Agent              │
          │ 候选 C：多 Agent Team         │
          │ 候选 D：人工与 Agent 混合方案 │
          └───────────────────────────────┘
```

### 3.2 AgentTeams 的职责边界

AgentTeams 是协同和运行底座，负责承载身份、房间、通信、团队关系、Worker 运行和基础能力绑定。AgentFit 在其上提供：

- 任务与能力的语义转换；
- 候选能力图和 Agent 分区设计；
- 试验数据、门禁与评测；
- 证据、审批、风险和回滚；
- 方案交付与跨项目经验沉淀。

本方法论不依赖对 AgentTeams 上游实现细节的重新定义，也不将底层框架能力误写成 AgentFit 已验证的场景能力。

### 3.3 常驻元团队

常驻元团队包含五个固定专业 Agent：

| Agent | 核心职责 | 独立责任输出 |
|---|---|---|
| EngagementLead | 接收任务、协调阶段、控制审批和交付 | 项目状态、审批决定、最终交付 |
| BusinessEngineer | 理解材料、抽取任务语义和自动化边界 | TaskSemanticSpec |
| AgentArchitect | 盘点能力、构造能力图、候选与 Agent 分区 | Capability Registry、CandidateGraph |
| ValidationEngineer | 部署候选、执行内循环和统一试验 | Trial Run、Execution Trace |
| GovernanceAuditor | 独立评测留出集、安全、证据与复杂度 | EvaluationReport、审计结论 |

五个角色不是为了满足数量要求而拆分。它们分别拥有独立任务、决策边界、上下文、责任产物和审计关系，符合本规范对 Agent 的定义。

## 4. 语义编译

语义编译不是对 PDF 做摘要，也不等同于生成向量。其目标是把自然语言材料转化为结构化、可比较、可计算和可审计的中间表示 AgentFit Semantic IR。LLM、Embedding、规则、Schema 映射、知识图谱和人工标注都可以参与该过程，方法论不预设必须使用其中任何一种。

### 4.1 任务语义

用户的需求、问题、想法、流程、样例和约束属于任务语义。任务语义定义目标函数与评测协议，回答“要解决什么，以及什么结果才算解决”。

```text
TaskSemanticSpec = {
  objective,              任务目标
  input_space,            输入类型、来源和数据范围
  expected_output,        输出结构、质量和证据要求
  examples,               正例、反例、边界例和历史案例
  distribution,           任务来源、变化范围和已知偏差
  metrics,                正确性、稳定性、成本、时延等指标
  tradeoffs,              指标之间的优先级和可接受交换
  acceptance_thresholds,  验收门槛
  budgets,                成本、时间、步数和资源预算
  risk_constraints,       数据、权限、安全和合规约束
  failure_costs,          漏判、误判、超时和错误执行代价
  human_boundaries,       必须人工审批、复核或承担责任的边界
  evidence_requirements   每类结论所需证据
}
```

任务语义在候选比较期间必须保持稳定。任何影响验收结论的修改都应产生新版本，并触发候选重评估。

### 4.2 能力语义

可调用的 Skill、MCP、工具、模型、规则、记忆、通信和人工能力属于能力语义。能力语义定义搜索空间，回答“有什么可以使用，以及怎样安全组合”。

```text
CapabilitySemanticSpec = {
  capability_id,          稳定标识和版本
  capability_type,        Rule / LLM / Skill / Tool / MCP / Human / State
  purpose,                能力解决的问题
  applicability,          适用任务类型、场景域与已知边界
  input_contract,         输入 Schema 与前置条件
  output_contract,        输出 Schema 与质量承诺
  trigger_condition,      适用条件与门控规则
  dependencies,           模型、系统、数据库、网络和其他能力
  cost_latency,           成本、时延和资源消耗
  permissions,            读取、写入、密钥和数据范围
  side_effects,           对外部系统和状态的影响
  failure_modes,          失败、异常、超时和不确定性
  recovery,               重试、降级、回滚和人工接管
  observability,          日志、Trace、指标和证据
  compatibility,          可组合和互斥关系
  scope_policy,           私有、团队、项目或全局共享
  reuse_value             同域复用和跨域迁移价值
}
```

Skill、MCP 和 Memory 可以是私有或共享资源。共享资源不会自动合并 Agent，私有资源也不会自动生成 Agent。

比赛手册中的 Skill 清单只是构建能力语义的一类原始输入，可以按以下方式适配到 `CapabilitySemanticSpec`：

| 比赛 Skill 字段 | CapabilitySemanticSpec 字段 |
|---|---|
| 使用场景 | purpose、applicability |
| 输入参数 | input_contract |
| 输出结果 | output_contract |
| 调用条件 | trigger_condition |
| 依赖工具 / 系统 | dependencies |
| 失败处理 | failure_modes、recovery |
| 权限与安全 | permissions、side_effects、scope_policy |
| 复用价值 | reuse_value |

这个适配只负责把比赛要求的 Skill 描述纳入能力注册表，不能代表 AgentFit 到 ML 的整体方法映射。

### 4.3 AgentFit 整体方法到 ML、NAS 与 Meta-learning 的映射

AgentFit 借用的不是某个 Skill 的 ML 类比，而是一套覆盖问题定义、搜索空间、候选结构、局部适配、全局选择和跨任务学习的完整方法论：

| AgentFit 方法对象 | ML / NAS / Meta-learning 语义 | 映射说明 |
|---|---|---|
| 业务材料、问题和历史案例 | 原始数据与问题来源 | 尚未形成可训练、可评测对象的原始材料 |
| TaskSemanticSpec | 学习问题与评测协议 | 定义输入空间 X、目标输出 Y、任务分布、指标、损失、约束和验收阈值 |
| 训练样例与留出样例 | Train / Validation / Test Split | 候选配置只使用训练样例，留出样例用于选择和审计 |
| CapabilitySemanticRegistry | 算子集合与假设空间 | Rule、LLM、Skill、Tool、MCP、Human 和 State 构成可搜索能力集合 |
| Task–Capability Alignment | 可学习性与特征/算子覆盖分析 | 判断现有能力是否足以表达任务，以及缺口、冲突和不可观测部分 |
| 基础能力图 G | 计算图与模型架构 | 节点表示能力操作，边表示数据、控制、反馈和状态依赖 |
| DAG 主干 | 前馈计算图 | 表示有明确推进顺序和终止路径的主任务结构 |
| 局部 SCC | 循环网络或迭代精化模块 | 表示反思、工具反馈、验证和有界协商循环 |
| Agent 分区 Π | 模块划分与控制边界搜索 | 决定哪些子图拥有独立策略、状态、权限、生命周期和责任；不是传统 ML 中完全等价的单一对象 |
| Agentize | 架构变换算子 | 将普通能力子图提升为可独立决策和负责的模块，是 AgentFit 特有的搜索操作 |
| 参数 θ | 参数、超参数与配置 | 包括模型、Prompt、阈值、工具配置、预算、重试和局部策略 |
| 共享范围 ρ | 参数/状态共享策略 | 决定 Skill、MCP、Memory、数据和上下文的私有、团队、项目或全局范围 |
| Candidate = (G, Π, θ, ρ) | 一个完整候选模型 | 同时包含结构、模块边界、配置与共享策略 |
| 内循环 | Task Adaptation / Parameter Optimization | 在外部契约和 Agent 边界不变时优化局部子图与配置 |
| 外循环 | Architecture Search / Model Selection | 根据留出表现改变全局图、Agent 分区和共享结构 |
| EvaluationReport | 验证指标与模型选择证据 | 比较正确性、泛化、成本、风险、复杂度和可审计性 |
| Project Dossier 与 Trace | Experiment Tracking 与 Provenance | 记录数据、候选、配置、运行、审批和结论的完整来源链 |
| MetaAsset 与搜索先验 | Meta-parameters、Initialization 与 Transfer Prior | 从多个项目沉淀初始架构、Agentize 条件、能力组合和失败模式 |
| DeploymentBundle / RejectionReport | 模型部署、拒识或 No-deploy 决策 | 合法结果包括部署、部分自动化、保留人工和拒绝自动化 |

整体映射可以压缩为：

```text
任务语义定义：优化什么
能力语义定义：可以用什么搜索
能力图与 Agent 分区定义：候选长什么样
内循环定义：如何让固定候选变好
外循环定义：如何让整个任务结果变好
Meta-learning 定义：如何让下一类任务从更好的先验开始
```

因此，Skill 只是能力搜索空间中的一种可复用算子；任务语义、能力图、Agent 分区、内外循环和跨项目先验共同构成 AgentFit 的 ML 方法论映射。

### 4.4 技术中立性与更新范围

AgentFit 定义要被转换和优化的对象，不把 LLM 规定为唯一实现方式。不同阶段可以使用不同技术：

| 阶段 | 可采用的方法示例 |
|---|---|
| 材料理解与语义编码 | 规则解析、Schema 映射、Embedding、LLM、知识图谱、人工标注 |
| 任务—能力对齐 | 约束匹配、向量相似度、图匹配、聚类、矩阵分解或 SVD、检索与人工复核 |
| 候选生成与结构更新 | 启发式搜索、图搜索、进化搜索、贝叶斯优化、学习到的先验或人工设计 |
| 局部适配 | Prompt、模型和阈值优化，也包括表示维度、分解秩、检索参数、规则权重和工具配置 |
| 评测与选择 | 确定性指标、统计检验、约束门禁、Pareto 比较、人工评审或受约束的模型评审 |

这些方法可以更新三个不同层次的对象：

1. **表示更新**：改变材料编码、Embedding、特征基底或语义 IR 的内部表示；
2. **能力与方案更新**：改变能力覆盖判断、基础能力图、Agent 分区、参数和共享范围；
3. **任务契约更新**：根据新事实修改目标、分布、指标或验收条件。

前两类可以在对应内外循环中发生。第三类不能由优化器静默完成；任何影响目标或验收结论的任务契约变化都必须产生新的 `TaskSemanticSpec` 版本，经责任人确认后重新执行候选比较。Embedding、SVD 或 LLM 生成的新表示本身不是新事实，也不能覆盖原始证据。

### 4.5 任务—能力对齐

语义编译完成后，AgentFit 必须生成 Task–Capability Alignment，逐项回答：

- 哪些任务要求已经被能力覆盖；
- 哪些要求只有部分覆盖；
- 哪些要求没有能力支持；
- 哪些能力存在输入输出不兼容；
- 哪些能力需要人工确认或更高权限；
- 哪些能力可以共享，哪些必须隔离；
- 哪些要求无法验证；
- 哪些缺口必须在进入候选生成前解决。

能力缺口不能通过虚构 Agent 名称掩盖。缺少可验证能力时，系统应提出 Growth Proposal、请求补充材料、降低自动化范围或停止搜索。

## 5. Agent 的规范定义

### 5.1 定义

> Agent 是具有独立身份、任务所有权、决策闭环、状态边界、权限边界和责任边界的可执行子图。

一个 Agent 至少具有：

```text
Agent = {
  Identity,
  Objective,
  DecisionPolicy,
  ActionSpace,
  StateBoundary,
  PermissionBoundary,
  CommunicationPort,
  Lifecycle,
  TraceOwnership
}
```

决策策略可以由 LLM、规则或混合方式实现。关键不在于是否使用 LLM，而在于该主体能否基于目标和状态独立选择下一行动、停止、重试、委派、升级人工，并对规定产物负责。

### 5.2 不属于 Agent 的充分条件

以下对象本身不构成 Agent：

- 单次 LLM 推理；
- 只有 Prompt 和工具列表但没有独立任务所有权的角色；
- 按固定顺序运行且不能选择下一行动的 Workflow 阶段；
- 仅提供输入输出转换的 Skill；
- MCP、API、数据库或其他外部接口；
- Memory 或共享状态；
- 容器、进程、房间等部署与通信实体。

一个容器可以承载多个语义 Agent；多个容器也可能只是同一 Agent 的执行资源。运行拓扑不能代替语义判断。

### 5.3 Agent 与其他概念的关系

| 概念 | 规范定位 |
|---|---|
| Skill | 可复用的做事方法，可以表现为原子能力或可展开子图 |
| MCP / Tool | Agent 感知或改变外部世界的接口 |
| Memory | 保存状态的介质，可以私有、团队、项目或全局共享 |
| Communication | 跨 Agent 边界传递任务、状态、证据和产物的协议 |
| Workflow | 规定执行顺序、门禁和失败分支的外部结构 |
| Agent | 组合并支配能力子图的独立决策与责任主体 |

同一个 Agent 分区内部的调用属于内部数据流。只有跨越不同 Agent 分区的边，才构成 Agent 委派、协商、质疑或汇报。

## 6. 能力图与 Agent 分区

### 6.1 候选表示

候选架构统一表示为：

```text
Candidate = (G, Π, θ, ρ)
```

- `G`：基础能力图，包含能力节点、数据边、控制边、局部 SCC 和状态依赖；
- `Π`：Agent 分区，表示哪些可执行子图被赋予独立身份和责任边界；
- `θ`：模型、Prompt、Embedding、分解秩、阈值、重试次数、工具配置、规则权重和局部策略；
- `ρ`：Skill、MCP、Memory、数据和通信的私有与共享范围。

Agent 不是与 Skill、Tool 并列的普通节点，而是对能力子图施加身份、决策、状态、权限和责任边界的分区操作。

### 6.2 图元素

能力图可以包含：

- 原子操作节点：规则、LLM 推理、工具/MCP 调用、人工决策、记忆读写；
- 可复用模块：Skill，可以从调用者视角折叠为节点，也可以展开为内部子图；
- 数据和控制边：顺序、条件、并行、汇聚、产物传递和环境反馈；
- 状态依赖：私有状态、共享记忆和外部事实源；
- 局部 SCC：有界的反思、验证、工具反馈或协商循环；
- DAG 主干：保证整体任务具有可解释的阶段推进和终止路径。

“负边”尚未形成规范定义。在正式定义前，禁止组合、权限冲突和不得执行的路径应表示为搜索约束或门禁，而不是未经解释的运行时边。

### 6.3 Agentize

AgentFit 使用以下概念操作将子图转化为 Agent：

```text
Agentize(
  subgraph,
  identity,
  objective,
  decision_policy,
  state_boundary,
  permissions,
  communication,
  trace_responsibility
)
```

只有当子图需要独立决策、上下文隔离、权限隔离、并行执行、独立生命周期或独立审计责任时，才应 Agentize。否则应优先保留为 Skill、工具节点或 Workflow 阶段。

### 6.4 连续复杂度空间

Agentless、单 Agent和多 Agent是同一搜索空间的不同复杂度位置：

```text
固定规则 / 工具 DAG
→ 加入 LLM 能力节点
→ 将局部反馈子图形成 SCC
→ 将局部子图 Agentize
→ 形成单 Agent
→ 按上下文、权限、并行或责任边界拆分
→ 形成多 Agent 协同
```

候选数量和 Agent 数量都不是预设目标。每增加一个 Agent，都必须通过统一评测证明其边际价值。

## 7. 双层优化与 Meta-learning

### 7.1 内循环：局部适配

内循环在保持外部输入输出契约和 Agent 边界不变的前提下，使固定 Agent 或局部 SCC 变得更好。它可以调整：

- Prompt、模型和局部策略；
- Embedding、特征表示、分解秩、对齐阈值和规则权重；
- Skill、工具选择和调用顺序；
- 记忆策略和上下文压缩；
- 阈值、重试、预算和 SCC 终止条件；
- 不改变外部契约的局部内部拓扑。

内循环不能自行创建或销毁 Agent、改变整体任务目标、修改验收标准、扩大权限或改变责任边界。

### 7.2 外循环：全局架构搜索

外循环根据留出集表现、成本、复杂度、风险和审计结果改变全局候选：

- 增加或删除能力节点；
- 改变全局拓扑；
- Agentize 或取消 Agentize；
- 拆分、合并、创建或销毁 Agent；
- 改变通信方式与共享范围；
- 在 Agentless、单 Agent、多 Agent和人工混合方案之间迁移；
- 降级、停止或否决自动化。

内外循环构成双层优化：

```text
内循环：
θ*A = argminθ Ltrain(A, θ)

外循环：
A* = argminA [
  Lvalidation(A, θ*A)
  + λ1·complexity
  + λ2·cost
  + λ3·risk
  + λ4·unobservability
]
```

公式表达的是多目标约束关系，不意味着必须使用固定线性权重。正式评测可以采用硬阈值、Pareto 前沿和分层门禁。

### 7.3 Baseline-first 搜索纪律

外循环从能够覆盖核心契约的最简候选开始：

```text
固定 Workflow baseline
→ 仅在证据显示局部不足时增加反馈循环
→ 仅在需要独立决策或边界时 Agentize
→ 仅在单 Agent 存在上下文、权限、并行或责任问题时拆分
→ 选择满足验收条件的最小充分候选
```

不得因为比赛要求展示多 Agent，就把候选系统的每个阶段命名为 Agent。比赛所需的多 Agent 闭环由 AgentFit 元团队真实承担；候选系统应忠实反映搜索结果。

### 7.4 Step、Episode 与 Epoch

| 名称 | AgentFit 中的含义 |
|---|---|
| Step | 一次推理、工具调用或环境反馈 |
| Episode | 一个任务样例的完整执行 |
| Inner Epoch | 固定候选对全部训练样例完成一轮适配 |
| Outer Generation | 一次候选生成、内循环适配、留出评测和架构更新 |
| Meta Epoch | 跨多个项目更新搜索先验和模板资产 |

局部 SCC 的一次循环是 Step，不应称为 Epoch。

### 7.5 跨项目 Meta-learning

单个项目内部主要是双层优化和 NAS 式架构搜索。只有当多个项目的搜索轨迹被用于更新可复用先验时，才构成 Meta-learning。

跨项目可沉淀：

- 适合不同任务语义的初始架构先验；
- Agentize、拆分和合并条件；
- 高价值 Skill、MCP 和 Memory 组合；
- 常见失败模式和无收益复杂度；
- 评测、故障注入和安全模板；
- 同域模板与经验证的跨域模式。

新项目可以从这些先验起步，但仍必须使用自己的任务语义、数据和留出集重新适配和验证。

## 8. 项目工作流

AgentFit 使用固定 Workflow 骨架、Agent 通信协同和结构化共享状态：

```text
Intake
→ Discover
→ Architect
→ Approve
→ Trial
→ Audit
→ Deliver
→ Learn
```

| 阶段 | 主要输入 | 主要产物 | 核心门禁 |
|---|---|---|---|
| Intake | 用户材料与初始问题 | Project Dossier、范围声明 | 材料来源和责任人明确 |
| Discover | 原始材料、案例、现有系统 | TaskSemanticSpec、Capability Registry、AlignmentReport | 核心输入输出与验收可描述 |
| Architect | 双语义 IR 与能力缺口 | 基础能力图、候选、Agent 分区 | 候选可执行且复杂度有理由 |
| Approve | 候选、预算、权限和风险 | TrialSpec、审批记录 | 试验范围和回滚已批准 |
| Trial | 训练样例、候选和实验环境 | 内循环结果、Trace、故障记录 | 训练与留出数据隔离 |
| Audit | 留出集、Trace、成本和安全证据 | EvaluationReport、选择或否决建议 | 每条结论可追溯 |
| Deliver | 审计通过的候选 | 部署包、运行手册、回滚方案或 RejectionReport | 用户确认责任和风险边界 |
| Learn | 项目结果与失败模式 | 项目资产、域模板、Meta 先验候选 | 脱敏、参数化、回归测试和审计 |

Matrix 或其他通信渠道用于委派、讨论、质疑和人工介入；Project Dossier 是唯一可信项目状态；Trace 是决策、工具、权限、审批和运行证据。聊天内容只有被结构化写入后，才能改变正式状态。

## 9. 评测、停止与否决

### 9.1 数据隔离

候选配置和内循环只能使用训练样例。留出集应由 ValidationEngineer 执行、GovernanceAuditor 解释，且不得被 AgentArchitect 用于定向修改候选。数据版本、场景分布和污染风险必须记录。

### 9.2 评价维度

至少评估：

- 任务正确性与关键子群表现；
- 稳定性、重试和失败恢复；
- 成本、时延、步数和资源使用；
- 权限、数据和外部副作用；
- Trace 完整性和可复现性；
- Agent 与能力节点的边际价值；
- 训练与留出表现差距；
- 人工接管质量和责任边界。

### 9.3 停止规则

满足以下任一条件时，外循环应停止：

1. 当前候选达到全部硬性验收阈值，且不存在更简单的等价候选；
2. 连续若干代没有获得足够边际改进；
3. 已达到预算、时间或复杂度上限；
4. 核心能力缺口无法在授权范围内补齐；
5. 留出集暴露不可接受的高风险失败；
6. 人工责任无法安全转移；
7. 增加 Agent 或能力带来的成本与风险高于收益。

停止不等于失败。系统应输出部署、降级、部分自动化、保留人工或拒绝自动化中的一种明确结论。

## 10. 安全、治理与受控增长

候选和临时能力的增长必须经过：

```text
Growth Proposal
→ 明确能力缺口
→ 设计临时专家或 Skill
→ 人工批准
→ 最小权限隔离创建
→ 测试与故障验证
→ 独立审计
→ 晋升、返工或销毁
```

所有候选必须遵循：

- 最小权限和明确数据范围；
- 密钥由基础设施持有，不进入 Agent 上下文；
- 外部写入和高风险动作需要审批；
- 沙箱、超时、预算和最大循环次数；
- 输入、模型、能力、配置和数据版本可追溯；
- 故障分支、人工接管和回滚路径预先定义；
- 失败证据与成功证据同等保留；
- 项目资产进入共享库前必须脱敏、参数化、回归测试和审计。

## 11. 交付物

每个项目至少应形成：

1. `TaskSemanticSpec`：任务目标、输入输出、指标、权衡和边界；
2. `CapabilitySemanticRegistry`：可用能力、契约、权限、成本和范围；
3. `AlignmentReport`：任务要求与能力覆盖、缺口和冲突；
4. `CandidateGraph`：基础能力图、Agent 分区、参数和共享策略；
5. `AgentIdentity`：每个真实 Agent 的身份、决策和责任边界；
6. `TrialSpec`：训练/留出划分、预算、故障计划和验收门槛；
7. `ExecutionTrace`：输入、状态、工具、通信、权限、审批和输出；
8. `EvaluationReport`：候选比较、过拟合信号、复杂度和风险；
9. `ArchitectureDecision`：选择、降级或否决的证据链；
10. `DeploymentBundle` 或 `RejectionReport`；
11. `MetaAsset`：经审计后可复用的模板、Skill、评测或失败模式。

完整推导链应能回答：

```text
为什么这样理解任务
→ 为什么选择这些能力
→ 为什么形成这张图
→ 为什么这些子图需要 Agentize
→ 为什么该候选优于更简单或更复杂的候选
→ 为什么可以部署、必须降级或应该否决
```

## 12. 适用场景

以下表示方法论的适用方向，不代表当前仓库已经实现这些场景。

### 12.1 软件 Issue 到可验证补丁

```text
输入：Issue、代码仓库、运行环境
输出：补丁、测试和执行证据
指标：解决率、回归风险、成本和时延
候选：固定流水线、单执行 Agent、模块化 Agent 与 Workflow 混合方案
```

Agentless、SWE-agent、OpenHands 和 MASAI 已被用于验证统一建图方法。该校准证明同一能力集合可以表达无 Agent、单 Agent和多 Agent候选，但没有在统一模型、预算和数据上证明哪种公开设计更优。

### 12.2 用户反馈与算法问题定位

```text
输入：反馈、日志、数据版本、查询链路和历史案例
输出：问题分类、根因、证据、影响范围和建议
指标：准确率、漏判率、证据覆盖率和处理时间
候选：规则路由、单诊断 Agent、领域 Agent Team、人工复核
```

### 12.3 线上巡检与故障处置

```text
输入：告警、指标、日志和变更记录
输出：异常、根因、处置建议、恢复验证和复盘
指标：发现率、误报率、恢复时间和执行风险
```

### 12.4 客诉与服务问题处理

```text
输入：对话、订单、政策和历史记录
输出：分类、处理方案、执行结果和用户确认
指标：解决率、满意度、合规性和处理成本
```

### 12.5 数据质量与数据链路检查

```text
输入：数据、表结构、统计结果、血缘和变更记录
输出：异常、原因、影响范围和修复建议
指标：异常召回率、误报率、覆盖率和运行成本
```

### 12.6 文档、合同与合规审查

```text
输入：文档、规则、历史案例和责任约束
输出：风险项、证据、严重程度和人工复核点
指标：高风险漏判率、证据完整性和审查时间
```

高风险部分无法达到严格阈值时，正确结果应是限制自动化范围并保留人工最终责任。

### 12.7 研究与数据分析流程

```text
输入：问题、数据、分析约束和参考材料
输出：分析过程、代码、结果和验证证据
指标：正确性、可复现性、成本和证据质量
```

## 13. 公开设计校准结论

软件 Issue 场景的公开设计校准形成了以下判断：

| 设计 | 统一图中的实际结构 | 按本规范判断的 Agent |
|---|---|---:|
| Agentless | 固定的定位、修复和验证 DAG，LLM 不决定下一行动 | 0 |
| SWE-agent | 一个持续观察、选择工具、执行和反馈的 SCC | 1 |
| OpenHands | 通用行动—观察 Agent，可按需委派专业 Agent | 1 或更多 |
| MASAI | 测试、定位、修复和排序组成的模块化 DAG | 约 3 个闭环 Agent，其余为能力节点 |

该校准支持以下方法论判断：

- 使用 LLM 不等于存在 Agent；
- 项目作者将模块命名为 Agent，不足以满足规范定义；
- 同一基础能力图可以通过不同 Agent 分区形成不同复杂度候选；
- Agent 数量应是搜索变量，而不是先验目标；
- Agent 与固定 Workflow 的混合架构是合法且常见的结果。

参考资料：

- [SWE-bench](https://github.com/SWE-bench/SWE-bench)
- [Agentless](https://arxiv.org/abs/2407.01489)
- [SWE-agent](https://arxiv.org/abs/2405.15793)
- [OpenHands](https://arxiv.org/abs/2407.16741)
- [MASAI](https://arxiv.org/abs/2406.11638)

## 14. 比赛映射

原始要求见 [《新智基座》Agent Infra 参赛手册](../reference/新智基座-参赛手册.pdf)。AgentFit 的当前设计映射如下：

| 比赛关注点 | AgentFit 设计 |
|---|---|
| 不少于 3 个不同职能 Agent | 五个常驻元团队 Agent，具有独立任务和责任产物 |
| AgentTeams 为协同基点 | 元团队和候选团队运行于 AgentTeams |
| Skill 必选并可复用 | 语义编译、能力对齐、候选生成、试验、评测和审计沉淀为 Skill |
| 任务拆解与上下文传递 | 八阶段 Workflow、Task Envelope、Project Dossier |
| 工具调用与结果验证 | 能力语义契约、Preflight Lab、训练/留出分离和故障计划 |
| 证据沉淀与安全审计 | Trace、EvaluationReport、最小权限、审批和回滚 |
| 记忆/RAG/共享状态/可观测至少两项 | Project Dossier 作为共享状态，Trace 作为轨迹可观测 |
| 经验沉淀 | 项目资产、同域模板、失败模式和跨项目 Meta 先验 |

比赛叙事应同时保持两种一致表述：

**工程方法论表述：**

> AgentFit 将任务材料与能力资源编译为统一语义 IR，在能力图、Agent 分区、能力参数和共享范围构成的联合搜索空间中，通过双层优化寻找满足验收约束的最小充分架构。

**场景表述：**

> 把业务材料交给一支 Agent 解决方案工程团队。它会理解问题、盘点能力、搭建多个候选团队、真实试运行并比较证据，最终交付最合适的 Agent 方案；如果 Agent 不值得使用，它也会有证据地拒绝。

ML、NAS 和 Meta-learning 是严谨的方法映射，不应替代真实场景价值和可运行证据。

## 15. 证据等级与当前边界

当前已经确认的是方法论和架构定义：

- 任务语义与能力语义的分离；
- Agent 的严格定义；
- 能力图与 Agent 分区联合表示；
- Agentless 到多 Agent的连续复杂度空间；
- 内循环、外循环和跨项目 Meta-learning；
- 最小充分架构与有证据否决；
- 元团队、结构化状态、Trace 和八阶段闭环。

当前已经完成的是公开架构的语义校准。它证明该表示能够解释多种现有设计，但不证明 AgentFit 已经自动完成搜索，也不证明任何候选在统一实验中获胜。

仓库中已有的同步 Python 模拟器、预配置候选和确定性分数只能作为早期结构演示，不属于真实 AgentTeams 协同、自动搜索或业务效果证据。
