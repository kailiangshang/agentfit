# AgentFit 证据研究、成长机制与参赛交付设计

> 状态：已归档、已被取代，不再是当前执行基线
>
> 当前唯一方案：[AgentFit 整体方案](../../agentfit-solution.md)
>
> 日期：2026-08-07
>
> 适用范围：方案研究、跨场景项目集、元 Agent 团队成长机制、初赛材料准备和双版本文档治理
>
> 不包含：代码实现计划、AgentTeams 上游分析、未经验证的效果声明

## 1. 目标

AgentFit 下一阶段不直接扩张代码或继续堆叠概念，而是建立一条从真实证据到参赛表达的完整生产线：

```text
真实场景与公开证据
→ 跨场景项目级训练评测集
→ 单项目双层优化与资产沉淀
→ 跨项目复验与 MetaAsset 晋升
→ 内部完整方案
→ 比赛精简材料
```

这条生产线需要同时解决四个问题：

1. AgentFit 是否能够解释并处理不同类型的真实 Agent 协同任务；
2. 元 Agent 团队怎样在单个项目中形成可靠资产；
3. 多个项目的经验怎样经过验证后改善后续搜索，而不是简单复制模板；
4. 内部方法论、实验事实和比赛材料怎样共享同一事实源，避免宣传与证据不一致。

## 2. 已确认的设计决定

以下决定已经确认，后续研究和文档不得自行改变：

- 采用“证据优先、双版本交付”的总体策略；
- 方法论保持技术中立；LLM 是实现手段之一，不是语义转换、对齐或搜索的唯一方法；
- 先建立比赛硬约束，再选择和研究场景；
- 跨场景资产不是普通问答数据集，而是项目级 `Cross-Scenario Project Suite`；
- 每个项目必须同时描述任务语义、能力语义、候选架构和评测协议；
- 单项目内是双层优化，跨项目更新可复用搜索先验后才称为 Meta-learning；
- 自主成长必须经过证据、独立审计、版本和回滚门禁；
- 现有五个常驻元 Agent 暂不增加第六个角色；
- 内部完整版是唯一事实源，比赛精简版从它派生；
- 当前阶段只设计和研究，不将模拟结果表述为真实 AgentTeams 运行效果。

## 3. 证据标准与调研方法

### 3.1 证据等级

真实案例调研必须标注证据等级：

| 等级 | 类型 | 可支持的结论 |
|---|---|---|
| E1 | 生产案例，具有组织、运行环境和可核验结果 | 可证明场景真实存在，并说明已报告的落地效果 |
| E2 | 受控实验、正式论文或公开基准 | 可比较方法、指标和失败模式，但不能直接声称生产效果 |
| E3 | 可运行开源实现或官方参考方案 | 可验证结构、接口和复现条件，但不能自动证明业务价值 |
| E4 | 产品说明、概念示例或设计文章 | 只能作为场景假设或设计启发 |

所有研究结论必须分为：

- `verified_fact`：来源能够直接支持的事实；
- `agentfit_inference`：AgentFit 根据事实形成的设计推断；
- `open_question`：尚无法核验或仍需实验的问题。

不得把 E4 材料写成生产案例，不得补造来源没有提供的指标。

### 3.2 OpenCode 的使用方式

OpenCode 用于对固定来源做结构化抽取、跨案例对照和独立审核，不作为无约束的事实来源。

标准流程为：

```text
人工或主 Agent 选择官方来源
→ 保存标题、URL、日期和来源类型
→ 固定来源快照
→ OpenCode 按统一 Schema 抽取
→ 主 Agent 复核引用与事实
→ 写入 Evidence Registry
```

如果 OpenCode 无法访问来源、发生检索超时或没有给出可核验引用，该次结果不得进入正式资料。

### 3.3 技术中立的更新机制

AgentFit 的固定部分是任务语义、能力语义、能力图、Agent 分区和内外循环等方法对象，不是某一种模型实现。各阶段可以组合使用：

- LLM 推理和结构化抽取；
- Embedding 编码、检索和相似度对齐；
- SVD、矩阵分解、聚类和降维；
- 图匹配、SCC 分析、约束求解和搜索算法；
- 规则、统计模型、传统机器学习和人工判断。

这些方法可以更新语义表示、能力覆盖、候选图、Agent 分区、局部参数和跨项目先验。为了避免优化过程改变问题本身，更新必须区分：

| 更新对象 | 是否可自动发生 | 约束 |
|---|---|---|
| 编码、特征和语义 IR 的内部表示 | 可以 | 保留原始材料、方法版本和可追溯关系 |
| 能力对齐、候选架构和局部配置 | 可以 | 遵守内外循环可修改范围和评测门禁 |
| 任务目标、指标和验收标准 | 不可静默修改 | 产生新 TaskSemanticSpec 版本并重新审批、评测 |

因此，“使用大模型”不是 AgentFit 的核心创新，能够用适合任务的数据与算法持续更新问题表示和落地方案，才是方法论要表达的能力。

## 4. Cross-Scenario Project Suite

### 4.1 定位

`Cross-Scenario Project Suite` 是用于训练、适配、架构选择、留出评测和跨项目迁移验证的一组项目包。它不把所有场景压成同一种问答格式，而是保留每类任务真实的输入、行动、工具、状态、风险和输出差异。

### 4.2 单个项目包

每个项目包至少包含：

```text
ProjectCase = {
  source_evidence,
  raw_materials,
  task_semantic_spec,
  capability_semantic_registry,
  task_capability_alignment,
  candidate_space,
  adaptation_set,
  validation_set,
  holdout_set,
  stress_and_failure_set,
  budgets,
  safety_constraints,
  evaluation_protocol,
  expected_artifacts,
  provenance_and_license
}
```

其中 `candidate_space` 至少允许比较：

- 固定 Workflow 或规则方案；
- 单 Agent 方案；
- 多 Agent 方案；
- Agent 与 Human 混合方案；
- 降级或拒绝自动化。

并非每个项目都必须实际运行全部候选，但必须说明哪些候选合法、哪些被约束排除以及理由。

### 4.3 两层数据隔离

单项目内：

```text
adaptation/train
→ validation
→ holdout test
```

- 内循环只能使用 adaptation/train；
- 架构选择可以使用 validation；
- 最终审计只使用 holdout test；
- 压力、权限和故障场景独立记录。

跨项目间：

```text
meta-train projects
→ meta-validation projects
→ meta-test projects
```

- MetaAsset 从 meta-train 项目产生；
- 晋升条件在 meta-validation 项目验证；
- 是否改善冷启动和搜索效率只能在未参与资产生成的 meta-test 项目判断。

### 4.4 v0 项目组合原则

v0 只选择 4–6 个具有结构差异的项目，优先覆盖：

1. 固定 Workflow 已经足够的任务；
2. 需要单 Agent 或局部 SCC 才能达标的任务；
3. 因上下文、权限、并行或责任边界而需要多 Agent 的任务；
4. 必须保留 Human 审批的高风险任务；
5. 在当前能力和证据下应拒绝自动化的任务；
6. 一组语义相似但分布不同的项目，用于验证跨项目迁移。

场景选择不按行业数量评分，而按其能否区分架构选择、揭示失败模式和支持复验评分。

### 4.5 场景准入门禁

候选场景进入 v0 前必须满足：

- 有可核验来源或明确授权的真实材料；
- 输入、输出、失败和责任边界能够描述；
- 至少存在两种有意义的候选架构；
- 能够构造独立留出样例；
- 指标或人工评测协议可执行；
- 数据、许可证和外部服务边界明确；
- 能对 AgentFit 方法论形成新的区分性证据。

## 5. 元 Agent 团队的单项目闭环

五个常驻元 Agent 保持现有职责。成长不是增加无边界的自修改能力，而是围绕同一 `Project Dossier` 形成可审计的资产生产闭环。

| 阶段 | 主要责任 | 转换 | 产物 | 门禁 |
|---|---|---|---|---|
| Semantic Compile | BusinessEngineer | 原始材料转为任务语义 | TaskSemanticSpec | 输入、输出、指标和风险可描述 |
| Align & Architect | AgentArchitect | 能力注册表与任务要求转为对齐结果和候选 | AlignmentReport、CandidateGraph | 缺口和冲突不得被虚构 Agent 掩盖 |
| Trial & Inner Loop | ValidationEngineer | 固定架构下适配模型、表示、分解、规则和工具等局部配置 | θ*、ExecutionTrace | 不修改 Agent 边界、权限和验收标准 |
| Holdout Audit | GovernanceAuditor | 留出表现与风险证据转为独立结论 | EvaluationReport | 训练/留出隔离，每条结论可追溯 |
| Outer Decision | EngagementLead | 候选证据转为下一代或停止决定 | ArchitectureDecision | 满足停止规则，保留降级与否决选项 |
| Project Learn | 五角色协同 | 已审结果转为项目级可复用候选资产 | ProjectAsset | 仍带项目作用域，不得直接全局复用 |

单项目可以沉淀：

- 任务与能力语义版本；
- 经验证的能力组合；
- 候选图和 Agentize 决策；
- Skill、Prompt、阈值和预算配置；
- 评测、故障注入和人工审批模板；
- 失败模式、无收益复杂度和拒绝原因；
- 完整 Trace、报告和决策来源链。

## 6. 跨项目成长与 MetaAsset 晋升

### 6.1 角色制衡

- AgentArchitect 提出资产抽象和适用范围；
- BusinessEngineer 检查任务语义相似性与领域边界；
- ValidationEngineer 在其他项目执行复验；
- GovernanceAuditor 检查污染、负迁移、安全和证据完整性；
- EngagementLead 批准晋升、冻结、降级或回滚。

### 6.2 晋升协议

```text
ProjectAsset
→ 脱敏
→ 参数化
→ 标注适用域与失败边界
→ 在其他项目重新适配
→ 与无先验 baseline 比较
→ 污染和负迁移检查
→ 独立审计
→ 版本化 MetaAsset
→ 持续回归与回滚
```

每个晋升资产必须包含：

- 稳定 ID 和语义版本；
- 来源项目和证据引用；
- 适用任务分布与不适用条件；
- 参数槽、默认值和允许范围；
- 成功与失败的跨项目复验结果；
- 数据污染检查结果；
- 与无先验 baseline 的迁移收益；
- 回归样例、降级路径和上一稳定版本。

### 6.3 三种学习层级

| 层级 | 定义 | 能否称为 Meta-learning |
|---|---|---|
| 项目内双层优化 | 当前项目中优化 θ 并搜索 G、Π、ρ | 否 |
| 跨项目资产复用 | 使用已验证模板作为新项目起点，并重新适配和审计 | 仅是迁移与复用 |
| 跨项目先验更新 | 多项目轨迹系统性更新候选生成、Agentize 条件和搜索顺序，并在未见项目验证 | 是 |

### 6.4 防污染和负迁移

发生以下任一情况时不得晋升或应立即冻结：

- 资产包含可识别业务数据、密钥或不可授权内容；
- 新项目留出集与原项目训练材料重合；
- 使用先验后的留出表现低于无先验 baseline；
- 资产只在单一项目或单一模型配置下成立；
- 适用域、前置条件和失败模式无法解释；
- 新证据推翻原结论，但版本仍被后续项目默认引用。

## 7. 初赛研究与证据材料包

官方要求以 [《新智基座》Agent Infra 参赛手册](../reference/新智基座-参赛手册.pdf) 为准。初赛调研不拆成大量孤立文档，而应收敛为七个材料包。

### 7.1 场景与价值包

- Agent 解决方案工程这一真实场景的需求来源；
- 代表性输入材料和期望交付物；
- 当前人工方案、重型平台和轻型框架的成本与断层；
- 可量化 baseline、目标和行业复制矩阵；
- 主演示项目与跨场景验证项目的关系。

### 7.2 多 Agent 协同包

- 五份 Agent Identity；
- AgentFit 概念到 AgentTeams 能力的映射；
- 八阶段闭环的具体项目走查；
- 上下文、房间、共享状态和责任产物的流转；
- 异常、冲突、多方案选择、审批和回滚分支。

### 7.3 Skill 工程包

- 核心 Skill 清单及标准契约；
- Skill 与普通 Prompt、工具调用和一次性脚本的边界；
- 跨 Agent 和跨场景复用矩阵；
- 阿里云官方 Skills 的必要性和接入位置；
- 版本、质量验证、发布、降级和回滚规划。

### 7.4 评测与搜索包

- Cross-Scenario Project Suite v0；
- Agentless baseline 和复杂候选；
- 训练、验证、留出和跨项目划分；
- 消融实验、故障注入和安全测试；
- 正确性、成本、时延、复杂度、风险和可审计性；
- 最小充分架构、部分自动化和拒绝自动化案例。

### 7.5 Production 证据包

- 一次完整运行的输入、Trace、Log、Metrics 和输出；
- Project Dossier 状态变化；
- Agent、Skill、工具和人工审批 Span；
- 超时、失败、降级、恢复和回滚证据；
- 当前真实完成范围与尚未完成能力的明确声明。

### 7.6 工具、合规与开放包

- MCP 或等价工具集成契约；
- 模型、商业 API、闭源组件和可替代方案；
- 数据来源、授权、脱敏和保留策略；
- 第三方依赖和许可证；
- 计划开放的代码、Skill、Schema、评测集和文档边界。

### 7.7 参赛叙事包

- 500 字以内作品简介；
- 初赛 PPT/PDF；
- 元团队层与候选系统层的双层架构图；
- 主 Demo 故事线和异常分支；
- 当前进展、复赛计划和可验证材料；
- 评委可能追问的问题与证据索引。

## 8. 双版本文档体系

### 8.1 内部完整版

内部资料保存定义、证据、实验、决策和风险，是唯一事实源。目标结构为：

```text
docs/internal/
├── project-thesis.md
├── methodology/
├── evidence-research/
├── cross-scenario-project-suite/
├── meta-agent-team/
├── evaluation/
├── governance/
├── agentteams-mapping/
└── decisions-and-risks/
```

现有 `docs/architecture/agentfit-methodology.md` 仍是当前方法论基线。后续只有在具体协议经过审核后，才更新其规范性内容。

### 8.2 比赛精简版

比赛资料只引用内部已验证事实：

```text
docs/submission/
├── preliminary-introduction.md
├── preliminary-deck-outline.md
├── agent-identities.md
├── skill-catalog.md
├── evidence-summary.md
├── demo-storyboard.md
└── judge-q-and-a.md
```

比赛版的每一项完成度声明都必须能够反向定位到内部证据。未经验证的内容只能标记为设计、计划或待验证，不能写成已经实现。

## 9. 工作顺序与审批门禁

### 阶段 A：约束与来源

1. 固化官方初赛要求和评分映射；
2. 建立场景来源白名单和 Evidence Registry；
3. 定义 Cross-Scenario Project Suite Schema；
4. 选择 v0 的 4–6 个项目。

门禁：用户确认项目组合和来源质量后，才能进入统一建模。

### 阶段 B：建模与协议

1. 为每个项目编译任务语义和能力语义；
2. 构造候选空间和评测划分；
3. 完成 Semantic Compile、Agentize 和 Inner/Outer Loop 协议；
4. 完成 ProjectAsset 与 MetaAsset 晋升协议。

门禁：协议必须能在至少两个结构不同的项目中使用，不能只适配主演示场景。

### 阶段 C：证据与比赛材料

1. 形成初赛最低可验证证据包；
2. 生成 Agent Identity 和 Skill 清单；
3. 编写内部完整方案；
4. 从内部事实源压缩出 500 字简介和 PPT；
5. 做事实一致性与红线检查。

门禁：PPT 中的完成度、指标和演示声明必须与证据包一致。

## 10. 完成标准

本设计进入执行完成态至少需要：

- 具有 4–6 个项目的 v0 项目清单和可核验来源；
- 每个项目都有任务语义、能力语义、候选空间和评测协议；
- 至少一组跨项目迁移对能够检验先验是否有效；
- 单项目资产和 MetaAsset 晋升协议可审计、可回滚；
- 七个初赛材料包均有负责人、来源和完成状态；
- 内部完整版与比赛精简版不存在事实冲突；
- 所有未完成能力、模拟证据和未来计划被明确标注。

## 11. 尚待后续选择的问题

以下问题不阻塞本设计成立，但必须在对应门禁前由用户确认：

1. v0 的具体 4–6 个项目及主演示项目；
2. 真实生产案例、公开基准和开源实现的比例；
3. 初赛最低证据包采用真实 AgentTeams 运行、现有模拟器，还是二者并列；
4. 首批核心 Skill 的数量和边界；
5. 哪些资产计划在比赛期间或赛后开放；
6. 复赛阶段 AgentTeams 集成和真实工具接入的承诺范围。
