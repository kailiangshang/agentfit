## 1. 重设计原因

首版已做到事实边界清楚、文件可编辑、结构检查无溢出，但不具备比赛路演所需的表达质量：页面大量重复卡片，阅读节奏单一；文案更像方案文档摘要，缺少具体场景、因果关系和逐步解释；技术名词出现得早于问题理解，评委需要自行拼接 AgentFit 的价值。

新版保留现有米白、深蓝、青绿、橙色和琥珀色配色，重做信息架构、文案和页面构图。

## 2. 核心概念(Fit + 建筑师)

本稿不是技术方案说明书,而是一个让评委记住的路演。核心主张贯穿全稿:

> **企业缺的不是更多 Agent,缺的是"刚好够用"的那一个。AgentFit 给 Agent 量体裁衣。**

辅助类比:AgentFit 是 **Agent 的建筑师**——不砌砖(不造 Agent),画图纸 + 验房(决定该不该造、造几个、验收合格)。

"任务先于 Agent / 并列候选搜索 / 方案工程层 / 证据红线"是支撑故事的实现骨架,但路演以故事和概念为主轴,实现术语下沉到备注和附件。

## 3. 讲述目标

评委看完后应能直接回答五个问题:

1. 企业为什么不能直接选一个 Agent 框架开始开发;
2. AgentFit 具体替企业做了什么决策;
3. 为什么 Agentless、单 Agent、多 Agent和 Human 混合必须公平比较;
4. AgentFit 如何运行在 AgentTeams 上,而不是重新发明平台;
5. 当前哪些是设计、模拟和已验证事实,后续如何形成真实证据。

## 4. 双案例叙事

### 4.1 贯穿示意场景：用户反馈定位

使用以下问题贯穿第 2–4 页：

> 一家公司每天收到用户反馈，需要完成聚合、问题定位、证据核验和结论交付，但不知道应该使用固定 Workflow、单 Agent 还是多 Agent。

该场景只解释 AgentFit 方法，必须显示“示意场景，不是运行证据”。

### 4.2 官网参考案例

来源为 GOAI Agent Infra 官网当前页面：

`https://goaihz.com/tracks?track=infra`

核验日期：2026-08-10。官网列出的四个参考方向是：

1. 零人工运维；
2. 智能客服自主闭环；
3. 软件研发全流程协同；
4. 金融风控与理赔自动化。

第 5 页展示四个方向共享的五段闭环，不把它们误写成 AgentFit 已运行案例。第 6–7 页深挖“软件研发全流程协同”：先忠实拆解官网描述，再用 AgentFit 做一次设计模拟。所有模拟结论必须标记“设计模拟，非运行证据”，不得填写虚构成功率、成本或排名。

## 6. 文案规则

- 每页标题必须是结论句，不能只是名词标签；
- 每页只解释一个核心因果关系；
- 正文先写业务含义，再出现 Schema、候选图和 Trace 等术语；
- **术语必须配中文人话**(如 TaskSemanticSpec → 任务说明书),内部契约名不上正文;
- **禁止代码符号上 PPT**(如 `selected_candidate = null` 已删除);
- **前 3 页不出现实现术语**(让评委先认同问题,再讲方案);
- 每个关键概念用"是什么—为什么重要—产出什么"解释；
- 单个说明块不超过 3 行，单页不超过 3 个主要说明块；
- 不在正文堆字段清单，字段进入图中标签或附录；
- `AgentFit`、`AgentTeams`、`Agentless` 和五个元 Agent 中文名保持一致；
- 任何非真实运行内容使用"示意场景""官网参考案例"或"设计模拟"显式标注；
- 真实运行证据使用"证据待补"或"下一步"，禁止出现未经验证的量化成绩。

## 7. 版式规则

- 16:9，共 12 页；保留既有配色；
- 每页最多 3 个带边框的大容器，避免卡片墙；
- 优先使用路径、泳道、对照轴、分层剖面和因果箭头；
- 标题 28–34 pt，正文不低于 14 pt，脚注不低于 9 pt；
- 页面必须存在明确视觉焦点和留白，不能平均铺满；
- 官网案例页显示来源 URL 和核验日期；
- 所有内容使用 PowerPoint 原生可编辑文本与形状；
- `hands-on-deck inspect --issues` 必须返回 `slides: {}`；
- PPTX 和 PDF 均需逐页渲染检查。

## 8. 模拟边界

官网软件研发案例的模拟只验证 AgentFit 的设计过程是否完整：任务契约、能力盘点、候选假设、统一预算、Human 门禁和 TrialSpec。它不运行真实仓库、不生成补丁、不宣布候选胜负，因此不是 PoC 或运行证据。

模拟的合法结论是：

> 当前证据只支持进入受控试验；在统一输入、预算和安全边界下完成真实执行前，不选择 Agentless、单 Agent或多 Agent赢家。

## 9. HTML-first 视觉生产决策

原生 `python-pptx` 只保留为文件封装和元数据工具，不再承担逐个图形的排版。十二页先使用 1280×720 HTML/CSS 完成视觉设计，再由 `html2patch` 编译为 PowerPoint 原生文本、线条、容器和表格；只有无法稳定转译的复杂纹理或插画才允许以 SVG/图片嵌入，禁止把整页截图伪装成 PPT。

### 9.1 设计令牌

- **主背景**：午夜蓝 `#0B2236` 与骨白 `#F6F2E8` 交替，形成路演节奏；
- **主行动色**：青绿 `#1A8D85` 表示已定义、可验证和通过；
- **风险色**：珊瑚橙 `#F26B4B` 表示问题、缺口和警示；
- **门禁色**：琥珀 `#D6A43B` 表示 Human、待补证据和发布控制；
- **正文色**：深蓝 `#102A43`，辅助文字使用 `#53697C`；
- **字体**：标题和正文使用 `Noto Sans CJK SC`，状态、编号与 Trace 使用 `Noto Sans Mono CJK SC`；
- **共享网格**：左边距 72 px、右边距 60 px、顶部眉题 42 px、标题基线 84 px、页脚 686 px；
- **记忆性符号**：贯穿全稿的“节点—候选路径—证据 Trace”图形语言。

### 9.2 构图要求

- 架构、流程和对照关系必须先在 HTML 中成为真正的图，而不是带标题的卡片集合；
- 每页只保留一个主要视觉焦点，页面切换通过暗色陈述页、浅色流程页和证据账本页形成节奏；
- 箭头、边界、责任链和门禁必须表达真实语义，不把装饰线当作关系；
- 编译后的 PPTX 仍须通过 `inspect --issues`，并逐页与 HTML 渲染结果对照；
- HTML 是布局事实源，PPTX 是可编辑交付物，PDF 是最终审阅物。
