# AgentFit 初赛方案与路演冻结设计

> 决策日期：2026-08-11
>
> 状态：已获用户批准，作为 2026-08-16 初赛提交材料的唯一叙事与结构基线
>
> 适用交付：500 字作品简介、方案 PPTX/PDF、12 页主路演、5 页附录及相关提交清单

## 1. 冻结目标

在真实 AgentFit 运行证据尚未形成的情况下，先收敛一套完整、诚实、可提交的初赛方案。运行闭环用于后续替换进展与证据页，不作为方案冻结的前置条件，也不得反向改变已经冻结的产品定义。

本设计解决此前材料中的两套叙事冲突：

- `Fit / 量体裁衣 / 建筑师` 负责解释用户价值；
- `Agent Architecture Search` 负责解释核心技术方法；
- `Meta-learning` 只描述经跨项目验证后的成长方向。

三者是上下层关系，不是三个并列产品定位。

## 2. 唯一产品定义

### 2.1 一句话定义

> AgentFit 是运行在 AgentTeams 上的 Agent 方案建筑师。它把业务任务和可用能力编译为可搜索的架构空间，通过统一评测找到“刚好够用”的方案，也允许有证据地保留人工或拒绝自动化。

### 2.2 三层表述

| 层级 | 对外问题 | 冻结表述 |
|---|---|---|
| 产品价值 | AgentFit 为用户解决什么 | 给 Agent 量体裁衣，交付最小充分、可验收的方案 |
| 技术方法 | AgentFit 如何做出选择 | 任务语义 + 能力语义 + 受约束的 Agent Architecture Search + 统一评测 |
| 成长方向 | AgentFit 如何跨项目变好 | ProjectAsset 经脱敏、适配、比较和未见项目验证后，才可晋升为 MetaAsset |

### 2.3 禁止的产品表述

- 不把 `AgentFit = Agent Architecture Search` 作为完整产品定义；架构搜索只是核心方法，不包含全部语义编译、审批、审计和交付责任；
- 不把 Meta-learning 写成当前已实现能力；
- 不预设多 Agent 优于 Agentless、固定 Workflow、单 Agent或 Human 混合；
- 不把 AgentTeams 平台能力或历史 smoke test 写成 AgentFit 已运行证据；
- 不把设计模拟、公开案例和概念图写成真实运行结果。

## 3. 评委应带走的五个结论

1. 企业真正缺少的不是更多 Agent，而是决定该不该用、用几个、如何验收的方案工程层；
2. AgentFit 先理解任务，再盘点能力，最后比较候选，不从创建 Agent 开始；
3. Agentless、单 Agent、多 Agent和 Human 混合属于同一搜索空间，每增加一个 Agent 都必须证明边际价值；
4. AgentTeams 提供身份、通信、容器、Human、Skill/MCP 和共享能力，AgentFit 在其上增加方案设计、评测、审计和交付；
5. 合法结果包括全自动、部分自动化、降级、保留人工和拒绝自动化，诚实拒绝也是交付。

## 4. 交付结构：12 页主路演 + 5 页附录

主路演负责让评委理解问题、价值、方法、系统边界和当前状态；附录负责完整覆盖比赛硬约束。技术细节不得通过缩小字号强塞进主路演。

### 4.1 十二页主路演

| 页 | 结论式标题 | 核心内容 | 主要视觉 |
|---:|---|---|---|
| 1 | Agent 架构不该靠猜 | AgentFit 寻找“刚好够用”的方案；产品价值优先于技术名词 | 一个任务对应多种候选，最终落到 `FIT` |
| 2 | 企业不知道的，不只是“用几个 Agent” | 用用户反馈定位示意输入、输出、验收、责任和复杂度都未定义 | 一条业务输入引出四类决策问题 |
| 3 | 平台提供砖块，但企业仍缺一位建筑师 | 重平台和轻框架都没有替用户完成方案选择与证据闭环 | AgentTeams/框架 → 缺失层 → AgentFit |
| 4 | AgentFit 先量体，再裁衣，最后试穿 | 量体：任务语义；裁衣：能力语义；试穿：候选比较 | 三步单向流程及各自产物 |
| 5 | 无、单、多 Agent 是同一个搜索空间 | 用同一能力图解释 Agentless、局部 Agentize、单 Agent和多 Agent | 一张能力图的四个渐进版本 |
| 6 | 最简单的合格者获胜 | 统一输入、预算、指标、安全和 Human 门禁；复杂度作为成本 | 三条候选赛道汇入共同验收线 |
| 7 | 五个元 Agent 把方案选择变成责任闭环 | 五个角色、独立责任产物、Human 审批和交付回路 | 带回路和门禁的责任链，不是五张角色卡 |
| 8 | AgentTeams 让团队运行，AgentFit 负责选对方案 | 上下层边界；共享状态、Trace、Skill/MCP 和 Human 的落点 | AgentFit 方案层 / 项目档案 / AgentTeams 底座 |
| 9 | 不同行业，共用一种方案决策方法 | GOAI 官网四类参考方向共享“输入—判断—执行—验证—沉淀”骨架 | 四条业务泳道汇入共同骨架 |
| 10 | 最终交付的不是 Prompt，而是可验收方案包 | 架构、理由、证据、安全边界和五种合法结果 | 方案包展开图，拒绝决定与部署方案并列 |
| 11 | 方法已经收敛，真实运行证据仍待补 | 已完成、当前设计模拟、未完成和下一门禁严格分栏 | 证据状态账本，不使用虚假完成标记 |
| 12 | Fit：刚刚好，不多不少 | 回扣产品价值；Architecture Search 是方法；Meta-learning 是未来验证方向 | 产品价值 → 技术方法 → 成长方向三层收束 |

### 4.2 五页附录

| 页 | 内容 | 必须回答的问题 |
|---:|---|---|
| A1 | 六层 ML 映射与候选表示 | 任务、能力、候选、内循环、外循环和跨项目学习分别是什么；`(G, Π, θ, ρ)` 如何解释 |
| A2 | 五个 Agent Identity | Name、Role、Capabilities、Inputs、Outputs、Dependencies、Decision Boundary、Trace 是否完整 |
| A3 | 七个 Skill、官方 Skill/MCP 和上下文机制 | Skill 的十个字段、使用/不使用官方能力的理由、共享状态与轨迹可观测如何满足 4 选 2 |
| A4 | Human 门禁、风险、异常和回滚 | 哪些动作必须人工批准，拒绝、超时、污染、预算耗尽和不可逆操作如何处理 |
| A5 | 开放、依赖、许可和当前未实现范围 | 哪些资产计划开放、仓库当前状态、模型/API/数据/许可证如何披露，哪些能力尚未实现 |

## 5. 内容数据流与事实源

提交材料按以下单向链路生成：

```text
官方手册与赛事通知
  + 可复现运行证据（如有）
  + docs/agentfit-solution.md
  + 已核验证据卡与设计契约
        ↓
本冻结设计
        ↓
500 字简介 + ppt-outline.md
        ↓
17 页 HTML/CSS
        ↓
可编辑 PPTX
        ↓
同版 PDF
```

下游材料不得反向修改上游事实。运行证据尚未形成时，第 11 页保持“待补”状态；形成证据后只能替换进展、版本、指标和证据指针，不改变产品定义与主路演骨架。

## 6. 场景与证据边界

### 6.1 贯穿示意场景

用户反馈定位只用于帮助理解“任务未定义时不能直接创建 Agent”，必须标记“示意场景，非运行证据”。

### 6.2 官网参考案例

第 9 页使用 GOAI Agent Infra 官网公开的零人工运维、智能客服自主闭环、软件研发全流程协同、金融风控与理赔自动化四类方向，显示来源 URL 和核验日期。它们只证明场景广度，不证明 AgentFit 已运行。

### 6.3 软件研发设计模拟

软件研发可以作为四类案例中的具体解释，但主路演不展开完整模拟过程。详细任务契约、三个候选和 `requires_runtime_trial` 结论保留在研究材料或讲者备注中；不得虚构补丁、测试、成本、成功率或赢家。

## 7. 文案与视觉规则

### 7.1 主路演

- 每页只回答一个问题，最多三个主要信息块；
- 标题必须是结论句，先写业务含义，再出现技术名词；
- 第 1–4 页不出现公式、L1–L6、SCC、`G/Π/θ/ρ` 或 Meta-learning；
- 第 5–6 页只解释架构搜索的必要概念，不展示 `argmin` 公式；
- 公式、六层映射、完整 Schema 和十字段清单全部进入附录；
- HTML 标题建议 38–50 px，正文不低于 18 px，标签不低于 14 px，脚注不低于 11 px；
- 不允许通过 9–11 px 正文塞入信息；
- 不使用无来源量化数据、无法解释的绝对表述或悬空文件引用；
- 页面之间用任务、候选路径和证据链形成统一视觉语言。

### 7.2 附录

- 可以使用技术符号和表格，但正文仍不低于 14 px；
- 每页只覆盖一类官方要求；
- 所有来源、版本、当前状态和未实现边界必须可读；
- 设计契约必须标记为设计，不得使用“已实现”“已验证”“已开放”等完成态措辞替代事实。

### 7.3 视觉令牌

- 主背景：午夜蓝 `#0B2236` 与骨白 `#F6F2E8`；
- 主行动色：青绿 `#1A8D85`；
- 风险色：珊瑚橙 `#F26B4B`；
- Human 与门禁色：琥珀 `#D6A43B`；
- 正文色：深蓝 `#102A43`，辅助文字 `#53697C`；
- 字体：`Noto Sans CJK SC`；Trace、编号和符号可使用 `Noto Sans Mono CJK SC`。

## 8. 500 字简介约束

简介与主路演使用同一三层定位，必须包含：

1. 企业面临的方案选择问题；
2. AgentFit 的一句话定位；
3. 任务语义、能力语义和候选比较的核心路线；
4. 五元团队与 AgentTeams 的边界；
5. 最小充分方案或拒绝自动化的交付价值；
6. 真实、可核验的当前进展。

正文按包含标点的非空白字符计算不得超过 500；建议目标为 420–470 字，为平台计数差异预留空间。任何“正在实施”“已运行”“已开放”声明必须与准备看板和证据状态一致。

## 9. 提交前错误处理与降级

- 若运行证据未形成：保留“设计完成、真实运行待补”，不阻塞简介和方案提交；
- 若新页面无法稳定编译：先修 HTML/CSS 与生成链，不用整页截图替代可编辑 PPTX；
- 若某项比赛要求无法放入主路演：进入对应附录，不压缩主路演字号；
- 若来源无法核验：删除量化数字或降级为明确标注的项目主张；
- 若 README、简介、PPT 和看板状态冲突：以官方要求、可复现证据、总体方案和准备看板的顺序校正；
- 若截止前仍无可执行代码包：不提交可选代码包，不影响必交简介与 PPT/PDF。

## 10. 验收门禁

只有同时满足以下条件，才可标记初赛材料“可提交”：

1. 500 字简介在 500 字以内，且与本设计使用同一产品定义；
2. 主路演严格为 12 页，附录严格为 5 页；
3. HTML、PPT 大纲、PPTX、PDF 的页序、标题和关键结论一致；
4. PPTX 为原生可编辑文本和形状，不是整页截图；
5. 新 HTML 可在严格模式下编译；
6. PPTX 几何检查无溢出、裁切和非预期遮挡；
7. PPTX 和 PDF 均完成 17 页逐页视觉检查；
8. 比赛要求中的场景、Agent、协同、Skill、工具、上下文、验证、安全、开放和当前进展均可在主路演或附录中定位；
9. 所有量化声明有来源，所有完成态声明有证据或被降级为计划；
10. 红线清单、依赖、许可证、商业 API、闭源模型、数据授权和既有基础完成最终复核。

## 11. 8 月 16 日前的非目标

- 不以跑通完整 AgentFit 闭环作为方案提交前置条件；
- 不实现自动 NAS、全量候选搜索或跨项目 Meta-learning；
- 不开发独立前端、飞书集成或修改 AgentTeams 核心；
- 不同时展开六个 ProjectCase；
- 不为了填充路演而伪造运行证据；
- 不再扩展总体方法论，只修复提交材料的一致性、完整性和可提交性。
